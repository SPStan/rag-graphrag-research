Выполнен локальный Dense candidate run на 100 вопросах S500[200:300]; независимая попытка построения HippoRAG остановлена OpenIE acceptance gate до QA, строгая независимая оценка не готова. 26 сентября выполнено отдельное [диагностическое сравнение](COMPARISON_2026-09-26.md) этого графа с Dense на тех же 100 вопросах (F1 29,97% / 18,58%). Основание — [исходное задание](../3_1_student_track_v1.md). Сводка не заменяет его и не утверждает новизну без проверки литературы.

Уточнение от 23 сентября: до целевого benchmark выполняем [локальный MVP](LOCAL_MVP.md) на RTX 3070 и небольшой модели. Это отдельная предварительная конфигурация; пороги и модель основного исследования ниже не заменяются. Решение — [ADR-0001](../.adr/0001-local-mvp-and-agent-artifacts.md).

## Вопросы и критерии

**В1:** при одинаковых данных, LLM и эмбеддере когда графовый поиск окупается относительно dense RAG с учётом индексации?

Проверяем пороги исходного задания: HippoRAG 2 на MuSiQue даёт не менее +5 процентных пунктов F1 к dense RAG при стоимости запроса не выше 3×; на HotpotQA разрыв менее 2 п.п. Это гипотезы, а не известные свойства датасетов.

**В2:** позволяет ли выбор между RAG и графом сохранить не менее 95% F1 режима always-graph при стоимости запроса не выше 60% от него?

Каскад сравнивается с always-RAG, always-graph и случайным смешиванием при сопоставимой стоимости. Разность качества проверяется парным bootstrap. Порог маршрутизации выбирается без использования итоговой тестовой части. Отрицательный результат допустим.

## Единые условия

- Основные наборы: MuSiQue и HotpotQA, по 500 вопросов, корпус до 5500 пассажей. Seed подвыборки — 42; все supporting-пассажи сохраняются; ID публикуются. Если они не помещаются в целевой размер, это явно фиксируется до изменения протокола.
- Пилот: первые 200 ID зафиксированной выборки; первый dense smoke — 100 вопросов MuSiQue.
- Минимум систем: dense RAG, HippoRAG 2, RAPTOR. LightRAG — расширенный уровень.
- Целевая конфигурация по сообщению куратора: `iairlab/qwen3.8-27b` через LiteLLM и локальный BGE-M3. Возможности backend ещё не подтверждены полной проверкой.
- Общий reader, одинаковый top-5 и формат контекста; точные ревизии адаптеров фиксируются перед измерениями.
- Метрики: F1, EM, recall@5; доверительные интервалы; токены индексации, запроса и получения сигналов маршрутизации.

### Замороженный план сравнения для issue #7

Все три метода получают одни и те же упорядоченные ID из `data/ids/*_s500.json`, тот же корпус 5500 пассажей на набор и одинаковый reader/оценщик. Точные списки пилота и разделения для сигнала: [DATA](DATA.md) и [ADR-0015](../.adr/0015-pinned-comparison-and-signal-split.md). Таблица ниже — **план целевого API**, не результат его проверки:

| Метод | Генератор и эмбеддер | Retrieval/context для общего reader | Reader и разбор | Параметры и версия адаптера |
|---|---|---|---|---|
| Dense RAG | Цель: `iairlab/qwen3.8-27b`; локальный BGE-M3 | Косинусный поиск, top-5 исходных пассажей | Один и тот же шаблон по набору, `scripts.answer_parser.extract_reader_answer`; локальный MuSiQue шаблон — `hipporag2-musique-one-shot-v6` | План: temperature=0, seed=42; поддержку параметров, output/context caps и версию backend ещё проверить. Локальный адаптер `scripts/run_dense.py` существует; его текущий commit фиксировать в манифесте запуска |
| HippoRAG 2 | Те же плановые модели | Графовый retrieval/PPR, до пяти исходных пассажей; встроенный dense fallback отмечать | Тот же шаблон и parser; локальный MuSiQue путь есть в `scripts/run_hipporag.py` | Те же плановые параметры; upstream 2.0.0a5 commit `1438aba3fc44ff10573e5a5e1e7cc3c7f9794aff`, версия адаптера/индекса фиксируется в будущем манифесте |
| RAPTOR | Те же плановые модели | Иерархический retrieval, top-5 **узлов**; каждый узел может быть суммаризацией, а не исходным пассажем | Общий reader/parser; адаптер ещё не реализован | Те же плановые параметры; upstream revision, адаптер, уровни дерева и query mode нужно закрепить перед E1/E2 |

Различаются построение индекса и путь получения контекста; для читателя фиксируются шаблон, порядок входных фрагментов, лимит входа и политика обрезки. Локальный общий шаблон проверен только для MuSiQue; HotpotQA reader ещё нужно выбрать и заморозить до сравнительного прогона. У RAPTOR top-5 узлов не означает те же пять исходных пассажей или тот же объём текста: в E2 записывать тип/уровень и длину узлов, фактические reader input tokens и исходные passage IDs, если они прослеживаются. `recall@5` supporting **пассажей** для суммаризованных узлов нельзя напрямую сопоставлять с dense/HippoRAG; для top-5 узлов указывать passage recall@5 как `not comparable`. Если сохраняется связь узлов с исходными пассажами, покрытие их объединения публиковать отдельно как provenance coverage, с числом исходных пассажей; это не recall@5 и не доказательство наличия факта в тексте суммаризации. F1/EM сравниваются на одинаковых вопросах и reader; различие вида контекста раскрывается как ограничение.

По #8 локальный BGE-M3 подтвердил два вектора размерности 1024 и 19 prompt tokens. Первый короткий Qwen-запрос не сохранил usage и не вернул текст; последующая ограниченная диагностика с `chat_template_kwargs: {enable_thinking: false}` вернула ответ и per-response usage 23 input / 4 output, включая 0 reasoning tokens. Это проверка простой генерации, не JSON/OpenIE или benchmark. Куратор сообщил: контекст Qwen3.8 — 262k, имена моделей закреплены, явных ограничений LiteLLM на параллельность нет; это не измеренные пределы сервера. До E1/E2 нужны проверки структурированного extraction, версий backend и параметров генерации. Локальные параметры Qwen 3B/7B не переносятся автоматически в целевой протокол.

Повторно использовать готовый ответ разрешено только при совпадении упорядоченных question IDs, SHA корпуса/источника, digest генератора и эмбеддера, retrieval/top-k, reader template/parser, генерационных параметров, версии адаптера и оценщика. Иначе требуется новый результат или явное исключение. Пилот `S500[0:200]` входит в полную S500 и не образует отдельный независимый тест. Полная таблица S500 описательная; для сигнала #21 сначала фиксируются формула и направление на `S500[0:300]`, затем единожды оценивается `S500[300:400]`. Целевые answers на проверочной части можно вычислить заранее, но их метрики и gold не просматривают до заморозки сигнала. Прежний `holdout100` не получает статус нетронутого: MuSiQue позиция 482 уже документально разобрана с ответом.

## Учёт стоимости

Для каждого метода раздельно сохранять LLM input/output tokens и embedding input tokens по стадиям: индексация (включая внутренние OpenIE/summary запросы), retrieval/query embeddings, дополнительный сигнал и generation/reader. Повторные попытки, ошибки и fallback входят в фактическую стоимость и отдельные счётчики. Сохранять количество вызовов и wall time по стадиям; кэш и reuse отмечать явно. Неизвестный usage — `unknown`, а не 0; не суммировать его как точное число. Администратор снял прежний лимит 90M; для каждого запуска остаётся отдельный протокольный предел. Локальные Ollama tokens учитываются отдельно.

Для N запросов полная стоимость в токенах: `T(N) = I + N*q`; средняя на запрос: `C(N) = I/N + q`. Здесь I — индексация, q — средний расход на вопрос. Сетка N: 100, 1000, 10000, 100000.

При простом сравнении токенов `N* = (I_graph - I_rag)/(q_rag - q_graph)` имеет смысл только при положительном конечном пересечении. Если его нет, сообщаем, что окупаемость не достигнута. Сравнение стоимости на верный ответ рассчитывается отдельно с явно указанной метрикой правильности; F1 не подменяет долю полностью верных ответов.

Каскад учитывает уже выполненный RAG, стоимость сигнала и граф на эскалированных вопросах. Значения берутся из `usage`; отсутствующее поле означает неизвестный расход, а не ноль. Административного лимита 90M больше нет; бюджет будущего эксперимента нужно закрепить отдельно. Локальные mock-проверки не входят в научные таблицы.

## Архитектура и результаты

Langfuse хранит трассы операций и вызовов. MLflow — конфигурацию, метрики и файлы прогона. JSONL в `results/` должен содержать ID вопроса, ответ, систему, датасет, фазы расхода и общий run_id со ссылками на трассы. Для локальных Dense и HippoRAG run уже проверен post-hoc экспорт с общим run_id, артефактами MLflow и локальными traces Langfuse. Это не заменяет планируемый cost proxy для целевого API: он должен инструментировать вызовы во время эксперимента.

Планируемые модули: `backends/`, `router/`, `eval/`, `data/ids/`, `configs/`, `tests/`. Они будут добавляться вместе с работающим кодом, а не пустыми заглушками.

Обязательное ядро: E1–E4 на двух наборах и минимум трёх системах; N*, oracle; E5–E6 с одним сигналом. Расширения: четвёртая система, дополнительные сигналы, E7, ablation и OOD. Сроки и сокращение объёма согласуются по фактическому прогрессу.
