# Работа с Res NIR Bot

Правило проекта по разбору предоставленного пользователем экспорта переписки
30.09–15.10.2026 (PR #24, #26, #28–#32). Это обобщение наблюдений,
а не регламент внутреннего устройства бота. Экспорт, персональные идентификаторы
и вложения в репозиторий не переносим. Текущие условия issue и решения куратора
проверяем отдельно; статусы из истории не считаем текущими.

## Три независимые проверки перед merge

1. **Техническая готовность:** критерии issue выполнены, замечания разобраны,
   нужные тесты и CI подтверждены для актуального HEAD. «Нет новых замечаний
   в дельте» не означает полное ревью PR. Synthetic-тесты не заменяют реальный
   smoke, если он прямо требуется в issue. Smoke не доказывает качество метода.
2. **Научное согласование:** ровно один блок `research-approval` по AGENTS.md.
   Для текущих формулировок подготовить пользователю
   `/research_submit <PR_URL> <ISSUE_NUMBER>`, затем
   `/research_status <PR_URL>`. Нужны подтверждения всех текущих O/N/R/H.
   После изменения формулировок прежний статус нельзя автоматически переносить.
   Не отправлять повторный submit неизменной карточки ради напоминания:
   в истории это не давало повторного уведомления. Не действовать от имени куратора.
3. **Отклонения:** превышение согласованного числа запросов, продолжение при
   неизвестном usage и другие отступления требуют отдельного подтверждения,
   если это предусмотрено протоколом. Сохранить точную ссылку, текст решения
   и его область действия. Научное согласование само по себе их не покрывает.
   Уже полученное применимое согласие повторно не запрашивать.

Пока работа не завершена — Draft. После завершения и согласования с пользователем
— Ready for review. При незавершённых критериях/согласовании использовать `Refs #N`;
оно само по себе не создаёт закрывающую связь. Перед разрешённым merge завершённой
задачи — `Closes #N`, проверить Development/Linked pull requests. После merge
проверить закрытие issue и статус существующей карточки Project; отдельную карточку
PR не добавлять. Не сливать PR только на основании фразы бота «блокеров нет».

## Как передавать материалы без повторных кругов

- Каждое обращение самодостаточно: полный PR URL, issue, HEAD SHA, цель проверки,
  что изменилось после предыдущего ревью, результаты проверок и ограничения.
  Не отправлять отдельно «исправил» или файлы без ссылки и задачи.
- При недоступном diff подготовить безопасные небольшие текстовые вложения
  по файлам с путями, base/head SHA и списком состава. Зависимые transport/parser
  helpers приложить по необходимости. Для зависимого PR отделить свой diff
  от унаследованного. Полный корпус, ключи и private raw не прикладывать.
- При обрезке вложения разделить его; не повторять тот же большой файл.
  При `repo_readonly` различать текстовое ревью и реально опубликованное GitHub
  review. Ограничение доступа бота не является дефектом нашего кода.
- Не просить повторное ревью того же SHA без новых материалов или изменившегося
  согласования. После двух неудачных передач разобрать конкретную причину доступа,
  а не запускать эксперименты или слать одинаковое сообщение ещё раз.
- Указывать, что проверено самостоятельно, а что только заявлено автором/ботом.
  Недоступное ботy CI проверить своими инструментами, не выдавая это за его проверку.
  Команды Telegram готовить пользователю; отправка сообщений требует разрешения.

## Повторявшиеся технические ошибки: проверять по применимости

- До первого HTTP, включая измерительный: валидность задачи, бюджет, права записи
  и резервирование результата. Негативный тест должен подтверждать ноль запросов.
- Попытку фиксировать до POST, известный usage и время — до проверки ответа;
  timeout, неверные векторы/JSON и частичный usage не должны стирать известный расход.
- Суммировать все физические попытки и дочерние диагностики. Ограничения retry
  проверять на закреплённом SDK через подставной HTTP-транспорт, не только mock метода.
  Reservation должен действовать между output directories/worktrees и при конкуренции.
- Целостность журнала не равна полноте стоимости; producer_run_id не доказывает
  стоимость кэша. Повреждённый журнал не должен мешать сохранить failed manifest;
  известные суммы сохраняются с явной неполнотой. Экспорт tracking сохраняет её тоже.
- Отсутствующий каталог аудита — ошибка/ограничение, а не «упоминаний нет».
  Разделять исходный аудит до эксперимента и последующую историю использования.
- Проверять байты и состав SDK против закреплённого Git commit, а не только HEAD
  или совпадение двух рабочих копий. Относительные пути привязывать к data-root.
- Публиковать воспроизводимую безопасную команду для заявленных counts/SHA;
  один SHA недоступного скрипта недостаточен. Убирать устаревшие текущие статусы.

Не создавать новый общий framework ради этого списка: применять проверки к
изменяемому пути и критериям задачи, использовать существующие helpers и тесты.


## Описание PR и таблицы для научного ревью

Перед отправкой прочитай описание как короткий исследовательский отчёт:
задача → результат → интерпретация → ограничения → проверки и ссылки.
Укажи, что подтвердилось или не подтвердилось, и сопоставь качество со временем,
расходом и ошибками. Не приписывай данным причинность или независимость без проверки.

В основном тексте не нужны история коммитов, перечни SHA и повторяющиеся служебные
счётчики. Оставляй их в проверяемых приложениях. Таблица должна содержать числа
с единицами и разумным округлением, а не inline JSON/dict, None и длинные дроби.
Поясняй, по каким случаям измерены качество и расходы. Перед публикацией проверь
рендер Markdown, пробелы, Unicode и связность таблиц. Краткость не отменяет
раскрытия failures, unknown usage и условий согласования. Научную карточку
не переписывай ради красивого вывода после эксперимента.
