## Замечания по коду

### F1. Нет полного восстановления успешного extraction — блокирует real repair

`execute_openie_task` возвращает отдельно attempt metadata и values. `RepairJournal.complete(task, attempt)` сохраняет только metadata.
В синтетической проверке после reopen статус задачи сохранён, но extraction values в checkpoint отсутствуют.
После перезагрузки нельзя восстановить исправленные NER/entities для зависимых triples и state patch из одного такого журнала.
Нужно атомарно фиксировать private output, SHA/identity и завершение; public summary может оставаться без текстов.
`prepare_repair_clone` сверяет updates и ledger по passage/stage/status, но не связывает сами values с их digest: такой контракт тоже нужен.
Критерий R1 — восстановление output в новом процессе без повторного callback, а не просто чтение статуса completed.

### F2. Название crash-safe сильнее реально проверенных гарантий — важно для R1

На синтетических данных подтверждено:
- два заранее открытых экземпляра RepairJournal могут выполнить begin для одной и той же задачи;
- поле `prompt` внутри task проходит begin и попадает на диск, хотя в complete блокируются такие поля metadata.
По коду состояние self.data меняется до _save; ошибка записи оставляет изменённое состояние в памяти. Caller должен гарантированно прекращать работу либо writer должен откатывать/блокировать такое состояние.
Ограничить применение одним writer и валидировать все сохраняемые объекты до записи. Достаточна простая защита локального процесса, распределённый scheduler не нужен.
Completed journal означает окончание очереди; успешность extraction проверяет отдельный gate. Не смешивать эти статусы.

### F3. Отчёт context fit не связан с фактическими параметрами транспорта — блокирует model calls

`validate_context_preflight` сравнивает переданные model_digest/параметры со значениями отчёта.
`make_uncached_ollama_request` проверяет max_retries и передаёт только messages, output cap, response_format; model, temperature, seed и context унаследованы от llm config.
Нет общей проверки, что фактический llm config соответствует context report. В pinned infer запрос собирается из `llm_config.generate_params` и kwargs.
Тест с подменённым transport должен захватить полный payload и проверить его соответствие frozen protocol.
При любом исключении executor сейчас проставляет `transport_attempt_count=1`, даже если callback упал до транспорта; такой факт нельзя выводить из одного исключения.

### F4. Копия с новыми vectors ещё содержит старые graph и manifest — блокирует QA

`prepare_repair_clone` копирует исходные graph.pickle/index_manifest, затем заменяет OpenIE state и vectors и пишет repair_provenance.
Граф не пересобирается этим helper. Это промежуточный артефакт, не готовый индекс.
Нужен явный запрет QA до нового graph + manifest и проверка pinned graph path на synthetic fixtures с сетью, заменённой на fail-fast.
Это gap текущей интеграции; реальные старые результаты helper не изменял.

### F5. Недостающие интеграционные решения нельзя заменить бесконечными preflight

38 triple prompts зависят от будущего успешного NER. Требование проверить их все до любого NER образует цикл.
Проверка должна идти по этапам: известные prompts заранее, зависимые — перед их реальным вызовом; исходный контроль контекста сохраняется.
Точного tokenizer-backed fit пока нет. Выбрать ограниченный путь проверки или предложить отдельно разрешённое измерение; не заменять tokens байтами.
Не повторять read-only поиск tokenizer и обновление отчёта без нового основания.

### F6. Часть «новой инфраструктуры» уже реализована

В `run_hipporag.py` есть `install_no_truncate_embedding_api`, проверка ответа и instrumentation usage; в repair helpers — reconciliation ID и копирование.
Нужна их связка, не второй embedding HTTP-клиент. При интеграции проверить учёт успешного первого split, если вторая часть завершилась ошибкой.
Новые универсальные плагины, агенты и очереди задач сейчас не сокращают путь к исследовательскому результату.

## Что не следует обещать

- «Больше никогда не придётся прогонять» — недостижимо: сбой во время запроса может оставить неизвестный исход, а изменение научного протокола потребует нового измерения.
- Можно гарантировать более узкую цель: не повторять достоверно сохранённые корректные шаги при неизменном протоколе.
- 196 запросов — первый проход, не полный cost; токены локальной LLM не равны расходу Codex.
- Не переименовывать diagnostic results в benchmark и не ослаблять gate ради красивой таблицы.
- Нельзя обещать экономию лимита Codex в конкретное число раз: API-тарифы не определяют расход подписки.

## Работа моделей и цена координации

По официальному [каталогу OpenAI](https://developers.openai.com/api/docs/models) Sol предназначен для баланса возможностей и стоимости, Luna — для ограниченных массовых задач, Astra — для сложного reasoning.
Рекомендация именно для этого репозитория: Sol ведёт текущую repair-интеграцию и проверяет существенные изменения; Luna выполняет чёткие ограниченные задачи; Astra разбирает спорные методологические решения.
Схема «Sol один раз спланировал, Luna автономно делает всё исследование» сейчас оставляет сложные решения без проверки.
Один дополнительный read-only reviewer полезен на границе законченного блока, если пользователь его явно разрешит. Передавать ему diff, контракт и тесты; не поручать заново читать всю историю.
Без постоянного роя агентов, без автоматического повторного ревью каждой правки текста. Текущий аудит выполнен без подагентов.
