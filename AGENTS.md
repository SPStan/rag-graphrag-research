# Инструкции для работы над исследованием

## Контекст и источники

- Это учебное сравнение dense RAG, HippoRAG 2, RAPTOR и, при наличии времени, LightRAG.
- Для продолжения начинай с docs/HANDOFF.md и активного блока docs/TASKS.md. Это единственная текущая очередь; README — навигация, docs/SPEC.md — требования, .adr/ — решения. Читай дополнительные файлы по задаче, а не всю историю на каждом шаге.
- docs/LOCAL_MVP.md хранит историю локального этапа, одобренного руководителем 23 сентября 2026; ранние команды и «следующие шаги» не являются текущим разрешением на прогоны.
- У пользователя Windows, RTX 3070 8 ГБ VRAM, 32 ГБ RAM. Langfuse работает в Compose, MLflow запускается отдельно. Проверяй доступность сервисов перед использованием.

## Работа с пользователем

- Объясняй по-русски, коротко и по шагам: что делаем, зачем и как проверить результат.
- Пользователь учится. Не приписывай ему понимание, действия или результаты, которых не было.
- Экономь контекст: читай нужные файлы, избегай повторного опроса долгих операций. Заканчивай один блок демонстрируемым результатом; не создавай новые helper/отчёты вместо интеграции уже написанного кода. Два неудачных исправления одной причины — повод для короткого разбора, а не бесконечного цикла.
- Не запускай подагентов без явной просьбы. Если более сложная модель полезна, объясни причину до продолжения сложного этапа; не утверждай, что переключил модель самостоятельно.

## Git и PR

- Новая работа ведётся в тематической ветке codex/* и Draft PR в master. Не коммить непосредственно в master.
- Начальное описание PR пишет студент своими словами. Сохраняй его текст; итоговое описание для ревью можно подготовить с помощью LLM.
- Assignee: SPStan; reviewer: resurrectiontent; label новой функциональности: enhancement.
- Если reviewer нельзя назначить в Draft или не хватает прав, явно сообщи ограничение. Не добавляй пользователей в collaborators без отдельного разрешения.
- Содержательные коммиты после завершённых шагов; не подделывай прошлые даты и не дроби изменения для видимости активности.
- Перед ревью: проверки, актуальная документация, фактические результаты и ограничения. Не снимай Draft и не сливай PR, пока работа не готова и это не согласовано с пользователем.

## Данные, секреты и измерения

- Не коммить .env, API-ключи, mlflow.db, локальные хранилища MLflow, виртуальные окружения, веса моделей, полные датасеты и индексы.
- Не печатай секреты и полный docker compose config; для проверки используй --quiet.
- Не удаляй Docker volumes или базы ради исправления настройки.
- Фиксируй источник и ревизию данных, seed, ID, модель и квантование, параметры, версию кода, ошибки и счётчики токенов.
- Разделяй mock-проверки, локальный PoC и основной benchmark. Значения из литературы и toy_score не являются нашими результатами.
- Локальная LLM обрабатывает реальные токены. Отсутствующее usage — неизвестное значение, не ноль. Не выдавай расход локальной модели за расход внутреннего API.
- Не передавай правильный ответ и метки supporting в генерацию. Сравниваемые системы используют одинаковые данные и условия.

## Архитектура и проверка

- Существенные решения документируй в .adr/: контекст, альтернативы, причины, последствия, проверка и условия пересмотра.
- Записывай решения по мере принятия. Предложение и экспериментально подтверждённый выбор — разные статусы.
- Используй готовые библиотеки и сервисы, пиши только необходимую связку и оценку. Не добавляй пустые заглушки ради структуры.
- Не заменяй проверенное окружение несовместимыми пакетами; конфликтующие адаптеры при необходимости изолируй.
- Для изменения только Markdown достаточно проверить ссылки, diff и отсутствие секретов. Для логики нужны целевые тесты, соответствующие изменению.
- Доступные проверки: `git diff --check`, `.\.venv\Scripts\python.exe -m pip check`, `docker compose config --quiet`.
- `scripts/smoke_langfuse.py` и `scripts/smoke_mlflow.py` создают записи в запущенных локальных сервисах. Не запускай их без необходимости.
- Тесты: `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`. Тесты данных, метрик, runner и tracking уже есть. Интеграционные проверки данных используют data/raw; без них пропускаются. Для изменения запускай целевые тесты, полный набор — на границе блока; не повторяй без новых изменений. Прохождение unit tests не доказывает работу реального repair.
