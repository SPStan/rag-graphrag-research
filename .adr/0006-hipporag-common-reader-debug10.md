# 0006 — Общий reader для локального сравнения HippoRAG 2

- Дата: 2026-09-25
- Статус: принято для технического debug10
- Связанные записи: [ADR-0003](0003-local-ollama-models.md), [ADR-0005](0005-hipporag2-local-sample.md)

## Контекст

Первый общий прогон Dense/HippoRAG использовал разные reader-подсказки и JSON response mode у HippoRAG. Эти различия не позволяют интерпретировать ответную метрику как сравнение retrieval. Требуется выровнять генерацию, сохранив графовый поиск HippoRAG и общий оценщик.

## Рассмотренные варианты

1. Оставить upstream reader и сравнить метрики напрямую — отклонено: prompt и формат ответа отличаются от Dense.
2. Перевести Dense на upstream HippoRAG reader — отклонено для текущей проверки: Dense v6 уже закреплён, а смена его reader потребовала бы нового базового прогона.
3. Подставить закреплённый MuSiQue v6 template в HippoRAG и использовать общий парсер — выбрано. Общий кодовый тест сравнивает все сообщения reader побайтно по роли и содержимому.

## Решение

Для MuSiQue HippoRAG использует те же system/few-shot/user сообщения, что Dense v6, без JSON режима для QA и с `extract_reader_answer`. OpenIE сохраняет JSON response mode, поскольку он формирует структурированные сущности и тройки. QA-вызовы явно обходят SQLite cache, чтобы debug run подтверждал свежие вызовы модели; исторические результаты и кэш не удаляются. Индексация использует отдельный сохранённый graph state и embeddings, runner записывает новые/повторно использованные записи.

Ollama embedding запросы ограничиваются 18 отдельными входами в секунду даже при внешнем batch. На Windows большой batch не предотвращает исчерпание loopback-портов: [обсуждение Ollama #18392](https://github.com/ollama/ollama/issues/18392) описывает соединение на каждый вход и наблюдавшийся безопасный темп около 18 входов/с. Ограничитель относится к каждому входу и сериализует обращения.

## Проверка и ограничения

Run `a38d6e57-3a33-4ece-aedb-390736ae3a0d` завершён на первых 10 закреплённых MuSiQue ID. Все 10 QA-вызовов были cache miss; модель Qwen2.5 3B Q4_K_M; top-5; `temperature=0`, `seed=42`, `num_predict=512`, `num_ctx=4096`. Общий evaluator дал EM=0,300, token F1=0,380 и recall@5=0,783. Один ответ завершился по лимиту без `Answer:` и корректно получил пустой ответ. Полный набор тестов после правки — 67 тестов.

Это отладочная десятка, использованная при настройке; результаты не являются независимой оценкой и не доказывают превосходство одного метода. Графовый state содержит 5500 passages, 44 890 entities и 48 002 facts; в OpenIE state у 452 passages нет сущностей, у 35 — троек. Два прежних прерванных прохода не сохранили usage, поэтому накопленная цена построения графа неизвестна. Run manifest создан до фиксации изменений и поэтому не содержит Git commit; итоговый код описан этой записью и связанным коммитом. 7B-сравнение и 100-вопросный прогон остаются отложенными.

Пересмотреть протокол после аудита OpenIE покрытия и выбора независимой фиксированной выборки. Не менять prompt, модель, generation options, corpus или top-k внутри парного сравнения.

## Уточнение по воспроизводимости embeddings, 2026-09-25

В OpenAI-compatible `/v1/embeddings` Ollama 0.34.3 не принимает `truncate`; закреплённый исходник показывает, что этот endpoint преобразует запрос без соответствующего поля. Runner поэтому использует native `/api/embed` и передаёт `truncate=false`. Подготовка входа сохранена совместимой с upstream адаптером: переносы строк заменяются пробелами, пустая строка заменяется одним пробелом. Проверяется число векторов, размерность как матрица, конечность и ненулевая норма. Код фиксирует report/ID/data hashes, runtime и hashes используемых исходников в manifest; index storage изолируется fingerprint этой embedding-политики.

Для производительности runner отправляет до четырёх входов в один запрос с connection pooling и выравнивает старты запросов по числу входов, удерживая среднее ниже 18 входов/с. Ollama сообщает общий `prompt_eval_count` для пакета, поэтому этот счётчик остаётся на уровне пакета; per-passage token attribution намеренно неизвестен.

Официальный Ollama API задаёт `truncate=true` по умолчанию и документирует `truncate=false` как ошибку при превышении контекста: [API embed schema](https://github.com/ollama/ollama/blob/v0.34.3/docs/openapi.yaml). Проба на одном коротком тексте подтвердила native endpoint, 1024 измерения, 10 входных токенов и конечный ненулевой вектор. Исторические embedding events в локальных сохранённых попытках имели максимум 1356 входных токенов при контексте BGE-M3 8192; это поддерживает совместимость уже сохранённых векторов, но старые попытки не переписываются.

## Результат no-trunc rebuild и evaluator, 2026-09-25

Добавлены проверки на деление пакета после HTTP 400 и форму матрицы при одном query. Rebuild прошёл на отдельном namespace: 5500 passages, 44 883 entities, 48 000 facts; граф содержит 50 383 узла и 121 026 рёбер. В итоговом manifest `9cac28e5-2885-4510-b227-ecba06f1b3de` зафиксировано 10 свежих QA вызовов, а общий evaluator подтвердил хэш JSONL, completed status и ordered expected IDs. Результат — EM 0,300, token F1 0,380, recall@5 0,783; один ответ остановлен по `length` и без `Answer:` включён в знаменатель как пустой. Значения совпали с предыдущим debug10 на другом graph cache; это диагностическое наблюдение, не независимый результат.

Индексация завершилась через два предыдущих технических manifest: `70c6c590-7c2e-4315-938f-af5fe73644fa` и `a341ae75-f211-4e27-9d27-eed92ff7dc0a`. В первом usage embeddings итогового cache известен для passages (684 560 tokens) и entities (322 667); во втором для facts (1 179 570). Также известны 135 382 tokens повторённой частичной индексации фактов, не попавших в итоговый cache; usage одного отклонённого запроса неизвестен. Последний run использовал cache, поэтому его ноль новых index embedding tokens нельзя трактовать как нулевую стоимость индекса. Длительность полного построения по этапам и неизвестный usage не подменяются нулём.

На первом HTTP 400 формат native API не воспроизвёлся в контрольной короткой пробе. Runner теперь делит только отклонённый multi-input пакет; одиночная ошибка остаётся ошибкой run. Второй этап создал весь граф, а затем обнаружил одномерный вектор для списка из одного query; адаптер теперь возвращает матрицу для list input. Старые и новые raw manifests сохранены локально, но не коммитятся.

Тот же completed run проверен в MLflow и Langfuse. MLflow run `012cfff24a814219a4a1e4ff07d512f5` хранит параметры, метрики, trace `tr-a21481936644b58d549bfecaaa0095f2` и три артефакта; скачанные JSONL, metrics и manifest побайтно совпали с локальными. Langfuse trace `6fd2c221dc7ffc89f8014316e6e63fd3` содержит indexing, retrieval, generation и 50 passages, с генерационным usage 15891/1330. Это локальный post-hoc учёт Ollama.
