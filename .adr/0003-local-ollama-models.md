# 0003 — Ollama-модели для локального Dense RAG PoC

- Дата: 2026-09-23
- Статус: принято для отладки локального MVP; сравнение reader-моделей продолжается
- Связанные задачи: MVP-3 и 1.4; ADR-0001

## Контекст

На RTX 3070 с 8 ГБ VRAM нужно проверить полный путь без внутреннего API: dense embeddings общего корпуса, top-5 retrieval и генерацию ответа. Результаты этого пути нельзя выдавать за основной benchmark на целевой модели qwen2.5-72b.

## Варианты

1. Ждать внутренний embedding/LLM API: целевая конфигурация, но доступов пока нет.
2. Установить модели через Transformers: даёт контроль над Python runtime, но добавляет крупные CUDA-зависимости и отдельную работу по совместимости.
3. Использовать локальный Ollama: модели доступны через локальный HTTP API, а работа с embeddings и генерацией не требует новых Python-пакетов.

## Решение и причины

Для отладки используем Ollama, BGE-M3 `bge-m3:latest` и Qwen2.5 3B `qwen2.5:3b`. В первом успешном запуске Ollama API вернул BGE-вектор размерности 1024. API метаданные зафиксировали BGE-M3 F16, digest `7907646426070047a77226ac3e684fbbe8410524f7b4a74d02837e43f2146bab`, и Qwen2.5 3.1B Q4_K_M, digest `357c53fb659c5076de1d65ccb0b397446227b71a42be9d1603d46168015c9e4b`. `ollama ps` показал 100% GPU для обеих моделей и runtime context 4096 на момент проверки. В первом прогоне генерация в среднем заняла 0.43 секунды на вопрос и шла со скоростью 137.91 выходного токена/с.

В первом local PoC BGE-M3 построил embeddings 5500 пассажей за 102.35 секунды. На первых 10 закреплённых MuSiQue ID при top-5 получены EM=0.000, token F1=0.022 и recall@5=0.633. С более точной factoid-инструкцией на тех же ID и неизменном кэше embeddings recall@5 остался 0.633, EM — 0.000, token F1 повысился до 0.040. Reader стал чаще давать короткий ответ, но ряд ответов оказался неверным. Оба измерения — диагностические результаты малого среза, не benchmark.

Уточнение от 23 сентября 2026: прежние прогоны использовали собственный zero-shot prompt; второй также менял `num_predict` со 128 на 64. В них не зафиксировано обрезание ответа. Поэтому они не являются сравнением, где изменился только prompt, и не показывают подтверждённого улучшения качества. Исходное задание требует reader prompt HippoRAG 2. Для нового локального этапа добавлен адаптированный one-shot шаблон MuSiQue из `rag_qa_musique.py`; сырые прежние JSONL сохранены. При сверке использован upstream `main` на 23.09.2026, но точный upstream commit не сохранён, поэтому SHA256 шаблона в новом результате фиксирует конкретную локальную реализацию, а формальный сравнительный результат пока отложен. Следующий шаг — проверить новый reader и оценщик на малом срезе, а не сравнивать 3B и 7B.

Сравнение с `qwen2.5:7b` Q4_K_M остаётся будущим отдельным экспериментом: одинаковые закреплённые ID, top-5, BGE-M3, reader и параметры; меняется только генератор. До запуска сверить digest и фактическое GPU/CPU placement. Увеличение модели само по себе не гарантирует улучшение качества.

## Последствия

- Зависимости Python не меняются; Ollama вызывается через HTTP API.
- Embeddings кэшируются локально и привязываются к corpus fingerprint и model digest.
- JSONL фиксирует model digest, локальные prompt/completion token counts, задержку, retrieved IDs и run_id; локальные файлы и модельные веса не попадают в Git.
- Qwen2.5 3B и 7B сравниваются только как локальные PoC; ни один результат не подменяет целевой API benchmark.
- Скрипт принимает `--generation-model`, чтобы менять reader-модель без правки кода и сохранять digest каждой версии в результатах.

## Проверка и пересмотр

Модельный сравнительный запуск должен использовать тот же корпус, embeddings, 10 ID, top-5 и reader prompt; меняется только генератор. Проверяем model digest и GPU/CPU placement. Если качество reader улучшится, сначала запускаем 20 отладочных ID, затем связываем run с MLflow/Langfuse и только потом планируем 100 вопросов. Если recall@5 низок, отдельно улучшаем retriever и не смешиваем причины одним изменением.
