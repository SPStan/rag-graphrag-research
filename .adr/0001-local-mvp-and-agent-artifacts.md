# 0001 — Локальный MVP и инструкции агента в основном репозитории

- Дата: 2026-09-23
- Статус: принято; локальный RAG ещё не реализован
- Основание: обратная связь руководителя от 23 сентября 2026, переданная студентом; текущий инфраструктурный коммит 6879ec2.

## Контекст

Есть smoke-проверки Langfuse и MLflow, но нет настоящего RAG-прогона. Доступы к внутренней LLM и T4 не получены. Локально доступны RTX 3070 с 8 ГБ VRAM и 32 ГБ RAM. Руководитель поручил начать с MVP/PoC на локальных моделях и готовых пакетных решениях, вести разработку через Draft PR и сохранять архитектурные решения и агентские инструкции.

## Рассмотренные варианты

1. Ждать внутренний API: сохраняет исходную целевую конфигурацию, но задерживает проверку цепочки работы.
2. Делать только mock-тесты: удобно для отдельных проверок, но не выявляет ошибки реального поиска и генерации.
3. Сделать локальный dense RAG на небольшой модели: позволяет проверить весь путь и оценку; требует отдельного обозначения результатов и учёта ограничений памяти.

Для агентских инструкций рассмотрены основной репозиторий и отдельный overlay-репозиторий. Overlay удобен при независимом жизненном цикле инструкций, но сейчас потребовал бы синхронизации двух репозиториев для одного студента.

## Решение

Выбираем локальный dense MVP, затем проверку пакетных графовых/иерархических решений. Основной протокол исследования сохраняется; локальные результаты не подменяют результаты qwen2.5-72b.

Храним AGENTS.md и .adr/ вместе с кодом: руководитель видит инструкции, их изменения и решения в том же PR. Не создаём CLAUDE.md или другие дублирующие файлы для неиспользуемых инструментов.

## Последствия

- Ветка codex/local-rag-mvp и Draft PR на master открываются до основной реализации.
- Первоначальное описание PR пишет студент; итоговое описание разрешено готовить с LLM.
- Начинаем с 10–20 вопросов для отладки, затем 100 MuSiQue. Одинаковые ID и зафиксированные параметры обязательны.
- Выбор конкретного генератора и рантайма пока предварительный. Он получит отдельную запись после проверки совместимости и памяти.
- Локальные токены, качество, задержки и ошибки сохраняются отдельно от целевого benchmark.

## Проверка и пересмотр

Этот ADR фиксирует решение о направлении работы, а не успешный запуск модели. MVP завершён после настоящего прогона, проверки метрик и воспроизводимой команды. При проблемах памяти сначала уменьшаем batch/контекст или разделяем стадии, записывая изменения. При получении API проверяем целевую конфигурацию отдельно. Отдельный overlay рассмотрим, если появятся приватные или общие для нескольких проектов инструкции.
