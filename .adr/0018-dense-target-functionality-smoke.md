# ADR-0018: малый Dense smoke в целевой конфигурации

Статус: технический smoke обоих наборов завершён 8 октября; научное согласование/merge отдельно.

## Контекст и выбор

Issue #10 требует проверить цепочку Dense на пяти development-вопросах каждого набора. Полный S500 и отложенная часть не запускаются. Используем первые пять S500 ID, проверяя их принадлежность `signal_tuning_ids` и исключая `signal_check_ids` и резерв. Корпус содержит объединение всех supporting-пассажей этих вопросов и первые 20 других пассажей закреплённого корпуса; порядок исходного корпуса сохранён. Это корпус для проверки работоспособности, не для оценки качества поиска.

Повторно используем `run_dense.top_k`, нормализацию BGE-M3, reader и parser, журнал issue #9 и `evaluate_dense`. Небольшой orchestrator `run_dense_target` подключает локальный native Ollama embedding и удалённый OpenAI-совместимый HTTP reader. Он не использует HippoRAG/OpenAI SDK; проверка retry того SDK относится к будущему HippoRAG-запуску. Requests проверяется с реальным HTTPAdapter и подставным ответом urllib3, без сетевого подключения.

Для двух наборов используем один неизменённый MuSiQue one-shot reader. Альтернатива создавать новый HotpotQA prompt добавила бы новый фактор: для этого smoke выбираем одинаковый reader и явно раскрываем применение MuSiQue примера к HotpotQA. Формат ответа `Answer:`, cosine top-5, temperature=0, seed=42, output cap=512; reasoning выключается через проверенный `chat_template_kwargs`. Поддержка и фактическое применение параметров backend не выводятся из принятого HTTP-запроса.

Лимит 100 000 токенов на датасет: отдельно сохраняются локальные embedding и remote LLM input/output. До запроса применяется консервативная резервация по размеру UTF-8 JSON + 2048 + output cap, reader input ограничен 16 000 байт. Это оценка для предварительной остановки, не измеренный tokenizer/backend предел. Фактический usage проверяется после каждой попытки; неизвестный расход, превышение лимита, некорректный embedding, неполный ответ или отсутствие `Answer:` прекращают цепочку и запуск следующего набора. Повторов и кэша нет.

## Проверка и последствия

ID, SHA исходных файлов, малого корпуса и queries публикуются без текстов и gold. Raw rows, metrics, manifests и journal остаются локально. Failed manifest перечисляет принятые ID, незавершённые ID и ошибку; usage записывается раньше проверки ответа. Оценщик принимает реальные API-параметры вместо вымышленных Ollama `num_ctx`/`num_predict`.

Протокол проверяется offline-тестами; выполнение и метрики отражаются в безопасной summary. Пересмотреть при смене reader, порядка ID, модели, API-параметров или состава корпуса. Сравнительный вывод по десяти development-вопросам недопустим. 13 октября PR #28 слит в master. Ветка #10 обновлена merge master, чтобы сохранить исходные commit ID запусков и проверяемые SHA provenance вместо переписывания истории rebase. Raw, версии выполненных запусков и метрики не изменяются. Актуальное согласование #29 помечено ботом устаревшим и должно быть получено заново; технический smoke его не заменяет.

8 октября первый MuSiQue run на `afd60ab` принял один ответ и остановился на втором. Расход пяти физических попыток известен полностью; завершение QA из этого не следует. Для следующих запусков после разбора добавлено сохранение invalid reader response локально с SHA; исходный invalid response этого run не восстанавливается. Новых модельных вызовов после остановки нет; [сводка](../results/summary/dense-target-smoke.json) фиксирует ограничения.

По новому поручению пользователя выполнена одна диагностическая попытка на `a63b6d2`: старый parser считает встроенное в reasoning «Synthesize the answer:» вторым маркером, хотя response завершён и содержит отдельную финальную строку. Это воспроизведение причины, а не восстановление утраченного response. Выбран `standalone-answer-line-v1` в общей Dense-связке; legacy inline parser не изменён. Новая версия и metric suffix записаны явно, исходный plan сохранён с добавленной execution version. Prompt и cap512 не менялись. Альтернатива повысить cap отвергнута: diagnostic output195, finish_reason=stop, reasoning0.

Полные HTTP responses и фактические reader requests сохраняются локально до usage/структурной/parser validation; null/пустые choices и missing usage покрыты offline-тестами. Для резерва диагностического бюджета index разбит на batches по 8. Финальные run на `4a60f2d` завершили по пять ID MuSiQue/HotpotQA; оба оценены существующим evaluate_dense. Вторая remote диагностика не потребовалась: исправление проверено на сохранённом ответе offline. В сводке раздельно сохранены исторический failed run, диагностика и финальные runs, а также их совокупный расход.

## Уточнение 13 октября: повторное использование prior

Ревью выявило, что расход первой диагностики вычитался заново при каждом использовании одного prior manifest. Теперь сверяется вся цепочка дочерних запусков, её суммарный известный расход и полнота; наличие ребёнка запрещает третью попытку. Единственная вторая попытка атомарно резервируется рядом с каноническим prior manifest до manifest/транспорта, с fsync, без автоматического освобождения после аварии. Альтернатива — только поиск завершённых manifests — оставляет окно для параллельного запуска или сбоя до manifest. Цена выбранного решения: сбой до HTTP тоже потребляет разрешение на вторую попытку; это безопасный отказ, не фактический расход токенов. Проверка — offline CLI reuse, descendants/unknown usage, crash и concurrency tests. Пересмотреть при смене протокола числа попыток или общего бюджета; исторические результаты не переписывать.

Уточнение по следующему ревью: reservation принадлежит каноническому каталогу prior, а не output_dir. Иначе два worktree с разными каталогами результатов не видят claims друг друга. `Path.resolve()` связывает относительные алиасы того же prior с одной записью; регрессии A/B/C и конкурентных продолжений из разных каталогов подтверждают блокировку до HTTP. Для хранения reservation нужен доступ записи к каталогу prior; невозможность записи означает отказ до транспорта.
