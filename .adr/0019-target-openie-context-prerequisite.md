# ADR-0019: ограниченная проверка проблемных OpenIE случаев на целевом API

Статус на 14 октября: контракт deployment передан пользователем (262144 общий
context, output до остатка окна, vLLM 0.29.0, native Qwen HF tokenizer/template).
Пять prompts помещаются по локальному закреплённому tokenizer; сверка с
server usage, генерация и пригодность конфигурации не проверены.

Обновление: HF tokenizer/template закреплены на
`1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0`; counts с output caps 1024/3072
дают 1302–3793 токена. Точный HF commit deployment отдельно не сообщён:
первый разрешённый ответ должен сверить input count с usage.prompt_tokens.
Артефакты и ограничения — [OPENIE_TARGET_CHECK](../docs/OPENIE_TARGET_CHECK.md).
Ниже сохранён контекст решения до ответа пользователя; исходный preflight
и его статус blocked не изменяются задним числом.

## Контекст

Issue #11 требует до пяти сохранённых development-примеров, проверки контекста/ответа и не более двух исправлений одной причины. Исторические repair/NER attempts и остановленные checkpoints не возобновляются; исходные индексы сохраняются. Пользователь разрешил выполнение #11 и ранее разрешил передачу исследовательских входов целевому API, но подтвердил, что лимиты iairlab/qwen3.8-27b неизвестны.

## Решение

Расширить существующий `preflight_hipporag_repair_prompts` режимом `--target-api-check`. Выбор: минимум и максимум исторических response bytes для NER/triples с terminal truncated плюс один request_error без ответа. Это представители наблюдавшихся причин; отсутствующие группы не выдумываются. До/после фиксировать раздельно: исторический статус воспроизведён offline; целевой результат не получен, если контекст не проверен. Шаблоны и установленный SDK сверить с полным Python tree закреплённого HippoRAG. Кэш открывать immutable/read-only, исходные SHA проверить до/после. Частичный JSON с length не принимать; строгий OpenIE gate не менять.

Метаданные получать только GET /v1/models, /model/info, /v1/model/info с whitelist безопасных полей. Они не являются генерацией. Точные input tokens не заменять bytes или usage другой локальной модели. Если проверенного per-prompt fit нет, не отправлять chat completions, сохранить конкретный блокер и ready_for_indexing=false. У новой проверки отдельный run ID и пустой журнал модели; это ноль новых попыток, а неизвестный исторический расход request_error остаётся неизвестным.

## Альтернативы и последствия

Принять произвольное окно по похожему имени модели или локальный tokenizer: быстрее, но версия backend неизвестна и такой fit не подтверждён. Повторить старый repair или пересобрать корпус: выходит за объём и изменяет исторические данные. Выбранный preflight сохраняет проверяемые случаи и требует от провайдера context/output limits и tokenizer revision либо точного серверного счётчика. До этого #11 остаётся с блокером и зависимая индексация не готова.

## Проверка и пересмотр

Целевые offline-тесты выбора, отсутствующих групп, secret-safe metadata-only GET, относительного data-root и строгой классификации. Фактические SHA/результат в отчёте #11. После получения нужного контракта отдельно выполнить выбранные случаи с журналом попыток и бюджетом, изменяя одну причину за раз, максимум два исправления причины. Новый режим preflight сам не выполняет этот следующий этап.
