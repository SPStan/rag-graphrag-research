# ADR-0030: oracle по проверенным private E3 оценкам

Статус: реализован offline; научные формулировки нового PR ожидают согласования.

## Контекст

Issue20 требует Dense/Hippo oracle по 500 одинаковым ID каждого датасета.
E3 передал private ledger на 3 000 исходов; текущая публичная версия содержит
только tuning scores. В истории уже было раскрытие контроля, оно не отменяется.

## Решение

Использовать HippoRAG2, выбранный pilot200, без выбора по текущему oracle.
Переиспользовать строгий E3 loader с пересчётом из сохранённых ответов и журналов;
сверять весь ledger с этим пересчётом, входными SHA и версией evaluator.
Считать EM и F1 отдельно, а четыре группы — только по EM. Ошибки сохраняют
принятые pipeline-zero scores и входят в знаменатель 500.
CLI блокирует сеть, публикует агрегаты, run IDs/config и input/code hashes.
Per-question ID/scores, gold и членство в группах остаются private.

## Альтернативы

- Публичные tuning300: не выполняют критерий 500 пар.
- Доверять только ledger digest: не обнаруживает подмену scores вместе с digest.
- Повторить генерацию: не нужно и меняет исходные ответы/расходы.
- Выбрать лучший из трёх методов: меняет согласованную пару и завышает scope.

## Проверка и последствия

Контрольный пример, oracle EM, четыре группы, ID/score gate, permutation,
failed-case retention и CLI/rebuild/0HTTP проверяются offline.
Реальная команда повторно проверяет source pins, метрики/counts/usage E3;
повторный JSON/Markdown должен совпасть побайтно. Старые raw/plans не записываются.
Oracle — описательная верхняя граница среди двух ответов, не router и не
доказательство экономии. Контроль нельзя использовать для выбора сигнала.
Пересмотр нужен при другой паре методов, версии evaluator или составе ID;
такие версии нельзя молча объединять с текущим результатом.
