## 1. Что мы должны получить

Нужно провести исследование: **когда поиск с помощью графа даёт достаточно пользы, чтобы оправдать расходы, и можно ли включать его только для части вопросов**.

Пример: обычный поиск находит текст, похожий на вопрос. Но если для ответа надо соединить два факта из разных документов, граф связей иногда помогает найти оба. Построение этого графа заранее тоже требует работы модели. Мы должны измерить и пользу, и затраты, а не предполагать, что граф обязательно лучше.

Два вопроса из задания:

1. **В1 — сравнение систем.** Как меняются качество и стоимость у dense RAG, RAPTOR, HippoRAG 2 и LightRAG на одинаковых данных?
2. **В2 — выбор системы.** Можно ли сначала получить ответ обычного RAG и обращаться к графу, когда уверенности недостаточно, сохранив не менее 95% качества графа при стоимости не более 60% от него?

Пороги — проверяемые гипотезы. Отрицательный результат допустим: вывод «при этих условиях улучшения нет» тоже полезен, если измерения корректны.

Итоговые материалы:

- Репозиторий с инструкцией, конфигурациями, адаптерами систем и тестами.
- Сохранённые ответы на вопросы, расходы токенов и воспроизводимые таблицы результатов.
- Графики качества и стоимости, расчёт окупаемости, оценка маршрутизации.
- Препринт на английском на 8–10 страниц и презентация на 12–15 слайдов.

Согласно исходному заданию обязательное ядро: **две выборки, минимум три системы — dense RAG, HippoRAG 2 и RAPTOR, эксперименты E1–E4, окупаемость и oracle, затем E5–E6 хотя бы с одним сигналом уверенности**. Четвёртая система, все сигналы, E7, все ablation и OOD — расширенный уровень. Сокращение ядра требует обсуждения с преподавателем; на высокий балл ориентируемся на полный план.

## 2. Что означают инструменты из сообщения преподавателя

| Понятие | Простыми словами | Для чего в этой работе |
|---|---|---|
| Стенд | Собранное рабочее окружение, на котором можно повторять измерения | Запускаем разные системы в одинаковых условиях и получаем проверяемые результаты |
| Docker | Средство запуска программ в контейнерах вместе с их зависимостями | Поднимаем сервисы без ручной установки всех их компонентов в Windows |
| Docker Compose | Описание нескольких связанных сервисов в одном YAML-файле | Запускаем, останавливаем и проверяем сервисы стенда общими командами |
| Langfuse | Журнал выполнения приложения с языковой моделью | Видим отдельный вопрос, вызовы модели, длительность, ошибки и расход токенов |
| MLflow | Журнал экспериментов | Сравниваем прогоны: какая система, настройки, выборка, качество и стоимость |
| API | Адрес и правила обращения к чужому серверу из нашей программы | Отправляем запросы внутренней языковой модели |
| Эмбеддер | Модель, превращающая текст в набор чисел — вектор | Сравниваем вопрос и документы по смыслу |
| Индекс | Заранее подготовленная структура для поиска | Векторы у dense RAG, дерево у RAPTOR, граф у графовых систем |
| Токены | Единицы текста, которые обрабатывает языковая модель | Считаем объём входа и ответа; точное количество берём из API |
| Прогон / run | Один запуск эксперимента с конкретными настройками | Результаты разных запусков не перемешиваются |

Compose описывает сервисы, их сеть и постоянные хранилища. Пригодятся пять действий: запустить, посмотреть состояние, прочитать логи, остановить, снова запустить с сохранением данных. Это соответствует [модели Docker Compose](https://docs.docker.com/compose/intro/compose-application-model/).

**Наше разделение задач:** Langfuse отвечает на вопрос «что произошло внутри этого запроса?», MLflow — «чем этот эксперимент отличается от предыдущего?». Возможности продуктов частично пересекаются; такое разделение мы выбираем для удобства. MLflow умеет хранить параметры, метрики, версии кода и файлы результатов, даже если большую модель мы не обучаем. См. [MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking/).

Например, в Langfuse найдём ответ на вопрос №17 и его LLM-вызовы. В MLflow увидим итог всего прогона на 100 вопросах, его конфигурацию, таблицу ответов и ссылку на связанные трассы. Числа здесь появятся после измерения; демонстрационные значения не считаются результатами исследования.

**MLflow не назван в исходном `.md`.** Включаем его в стартовый стенд на основании сообщения преподавателя и уточним ожидаемый объём: для начала достаточно Tracking, сохранения параметров, метрик и файлов.

## 4. Где будет работать стенд

Начинаем на личном Windows-компьютере. Сервер и внутренний API пока недоступны; их подключение — отдельная зависимость плана.

| Место | Что запускается | Что уточняем |
|---|---|---|
| Компьютер с Windows | Редактирование кода; при достаточных ресурсах — Docker Desktop и локальные сервисы | RAM, свободный диск, виртуализация, WSL 2 |
| Linux-среда: WSL 2 или учебный сервер | Python-окружение и экспериментальные скрипты | Совместимость библиотек, постоянное хранение, доступ к сервисам |

| Внутренний сервер LLM | Основная модель qwen2.5-72b и дополнительные модели | Адрес API, ключ, имена моделей, лимиты и поле `usage` |

Если позже преподаватель выделит Linux-сервер для всего стенда, сможем перенести туда конфигурацию и данные сервисов, а с Windows подключаться к нему. Пока настраиваем локальное окружение после проверки RAM и свободного диска.

Для Windows официальный путь установки Docker Desktop описан в [документации Docker](https://docs.docker.com/desktop/setup/install/windows-install/). Фактические ресурсы измерим на своём запуске. Источник: [Langfuse Docker Compose](https://langfuse.com/self-hosting/deployment/docker-compose).

RTX 3070 — локальная видеокарта, T4 — ресурс из задания. Временные проверки на своей карте возможны после настройки, но в отчёте нужно явно указывать реальное оборудование. Большую qwen2.5-72b по плану вызываем через внутренний API.

## 5. Из чего состоит первый стенд

```text
Скрипт эксперимента на Python
    |
    +--> Ретривер: dense RAG / RAPTOR / HippoRAG 2 / LightRAG
    |        |
    |        +--> bge-m3: получение векторов
    |        +--> свой индекс на диске
    |
    +--> Все обращения к LLM, включая индексацию и reader
             |
             v
        Прокси учёта --> внутренний API модели
             |
             +--> Langfuse: трассы и отдельные вызовы
             +--> results/: исходные записи о расходах

Скрипт эксперимента --> MLflow: параметры, итоговые метрики, файлы
```

Reader — общий шаг, на котором модель формулирует ответ по найденному контексту. Его настройки делаем одинаковыми для сравниваемых систем.

Планируемые сервисы:

- **Langfuse и его штатные зависимости.** По текущей официальной архитектуре это web, worker, PostgreSQL, ClickHouse, Redis/Valkey и S3-совместимое хранилище; в Compose-примере используется MinIO. Берём согласованный официальный Compose-файл и фиксируем версии. См. [архитектуру Langfuse](https://langfuse.com/self-hosting).
- **MLflow Tracking.** Для одиночного стенда начнём с явно заданной SQLite-базы и отдельного постоянного каталога артефактов. Если нужен общий сервер с параллельными пользователями, подберём серверную БД. Хранение зададим в конфигурации явно, чтобы не зависеть от значений по умолчанию. См. [MLflow Tracking Server](https://mlflow.org/docs/latest/self-hosting/architecture/tracking-server/).
- **Прокси учёта вызовов.** Наш небольшой сервис, который передаёт запросы внутреннему API и записывает фактический расход.
- **Сервер эмбеддингов.** bge-m3 с HTTP-интерфейсом, предпочтительно на T4.

Экспериментальный код сначала можно запускать в отдельном Python-окружении. Контейнеризация всех исследовательских библиотек сразу не является условием первого результата.

Для запуска одного стенда подготовим Compose-конфигурацию и файл с переменными окружения. Данные сервисов храним в постоянных томах. Секреты помещаем в локальный `.env`, а в репозитории оставляем `.env.example` без значений ключей.

Основные адреса в плане — `http://localhost:3000` для Langfuse и `http://localhost:5000` для MLflow, если порты свободны. Это адреса, которые предстоит настроить, а не уже работающие сервисы. Внутри контейнеров адреса могут отличаться: `localhost` там указывает на сам контейнер.

## 6. Ближайшая работа: шаги с проверкой результата

Один рабочий блок — примерно 2–2,5 часа. Начальные шаги могут занять **около 22–32 часов вместе с освоением инструментов**, то есть 2–3 недели при нагрузке из задания. Это предварительная оценка, а не обещание срока. Получение доступов и ожидание индексации считаются отдельно.

### Шаг 0. Определить место запуска и получить доступы

Время: 30–60 минут активной работы; ожидание ответов непредсказуемо.

Что делаем:

1. Выясняем, где преподаватель ожидает стенд: на личном компьютере или сервере.
2. Проверяем RAM, диск, права установки и наличие виртуализации на выбранной машине.
3. Получаем адрес внутреннего API, точные идентификаторы моделей и правила использования ключа.
4. Уточняем ограничения по запросам, параллельности, контексту и токенам.
5. Получаем доступ к T4 и выясняем, есть ли уже embedding endpoint.
6. Уточняем, нужно ли поднять собственный MLflow или подключиться к учебному.

**Результат:** таблица доступов и оборудования без секретов в `docs/environment.md`.

**Проверка:** понятно, на какой машине запускается каждый компонент и к каким ресурсам мы действительно можем обратиться.

**Что ты сможешь объяснить:** где выполняется наш код, где работает большая модель и зачем нужна T4.

### Шаг 1. Подготовить Docker и рабочее окружение

Время: 2–3 часа, иногда больше при проблемах с виртуализацией.

Зависимость: выбран компьютер или сервер из шага 0.

Что делаем:

1. На Windows настраиваем WSL 2 и Docker Desktop; на Linux — Docker Engine и Compose.
2. Проверяем работу Docker Engine и Compose, запускаем небольшой учебный контейнер.
3. На простом Compose-примере разбираем сервис, образ, порт, том и переменную окружения.
4. Осваиваем `docker compose up -d`, `docker compose ps`, `docker compose logs`, `docker compose stop`, `docker compose down`.
5. Создаём структуру проекта, `.gitignore` и изолированное Python-окружение совместимой версии.

**Результат:** Docker запускает контейнеры, версии инструментов записаны, рабочее окружение воспроизводится.

**Проверка:** учебный сервис отвечает; после остановки и повторного запуска сохранённые данные остаются. Команда удаления томов не используется для обычной остановки.

**Что ты сможешь объяснить:** чем образ отличается от контейнера, зачем нужен том, как посмотреть причину ошибки запуска.

### Шаг 2. Поднять Langfuse

Время: 2–3 часа.

Что делаем:

1. Берём официальный Compose-пример Langfuse для выбранной версии и фиксируем версию сервера и SDK.
2. Настраиваем переменные, постоянные тома и локальный доступ к интерфейсу.
3. Запускаем зависимости и проверяем их состояние.
4. Создаём проект и ключи подключения нашего приложения.
5. Отправляем тестовую трассу из небольшого Python-скрипта. Если API ещё недоступен, трасса явно помечается как демонстрационная.
6. Дожидаемся доставки событий и проверяем их в интерфейсе.

**Результат:** открывается Langfuse и видна тестовая трасса.

**Проверка:** событие отправлено программой, содержит ожидаемые поля и сохраняется после перезапуска сервисов. Простой факт открытия страницы ещё не означает, что трассировка работает.

**Что ты сможешь объяснить:** один trace объединяет работу над запросом; вложенные события показывают отдельные операции и вызовы модели.

### Шаг 3. Поднять MLflow и записать первый эксперимент

Время: 1,5–2 часа.

Что делаем:

1. Добавляем Tracking Server в Compose с постоянным хранением метаданных и файлов.
2. Подключаем Python-клиент через `MLFLOW_TRACKING_URI`.
3. Создаём эксперимент `rag-graphrag` и демонстрационный run.
4. Записываем параметр конфигурации, тестовую метрику и небольшой файл.
5. Перезапускаем сервер и повторно открываем run и его файл.

**Результат:** в MLflow есть воспроизводимый демонстрационный прогон.

**Проверка:** работает запись и последующее чтение метрик и артефактов. Демонстрационные метрики помечены и не попадают в научные таблицы.

**Что ты сможешь объяснить:** параметр — то, что мы задали; метрика — то, что измерили; артефакт — файл результата.

### Шаг 4. Проверить внутренний API и учёт токенов

Время: 2–3 часа.

Зависимость: доступ к API; проверку можно начать до завершения интерфейсов мониторинга.

Что делаем:

1. Отправляем один короткий запрос основной модели и сохраняем ответ вместе с `usage`.
2. Проверяем поддержку `logprobs`, `seed`, `temperature`; фиксируем не только успешный ответ, но и фактическое поведение параметров.
3. Для дополнительных моделей отдельно фиксируем доступные способы управления reasoning. Точное поведение внутреннего сервера проверяется экспериментально.
4. Создаём первую версию `eval/cost_proxy.py`, направляем через неё тот же простой запрос.
5. Сохраняем входные и выходные токены, время, статус, модель, фазу, систему и идентификаторы.
6. Связываем запись в JSONL, трассу Langfuse и run в MLflow общим идентификатором эксперимента.
7. Сверяем суммы на нескольких вызовах и проверяем поведение при ошибке.

**Результат:** один реальный вызов модели полностью прослеживается от запуска до записи расходов.

**Проверка:** числа из `usage`, исходных JSONL-записей и Langfuse совпадают; в MLflow записана та же сумма. Отсутствующее `usage` отмечается как неизвестное, а не как нулевой расход.

**Что ты сможешь объяснить:** откуда взялось число токенов и почему не нужно считать стоимость по длине текста на глаз.

**Первая демонстрация преподавателю:** Compose запущен, в Langfuse виден реальный вызов, в MLflow — связанный run с расходом и настройками. Если API ещё не выдан, показываем только явно помеченную демонстрацию инфраструктуры.

### Шаг 5. Запустить общий эмбеддер bge-m3

Время: 2–3 часа после получения доступа к GPU.

Что делаем:

3. Если готовый сервер несовместим с окружением, используем небольшую обёртку FastAPI над подходящей библиотекой.
4. Проверяем один текст, пакет текстов, размер вектора, порядок ответов и ограничения длины.
5. Фиксируем модель, ревизию, нормализацию и политику обрезки текста.
6. Измеряем время и скорость на реальных пассажах будущего корпуса.

**Результат:** общий endpoint эмбеддингов и сохранённая конфигурация.

**Проверка:** все системы смогут получать векторы одинаковым способом. Для dense-режима bge-m3 ожидаем векторы размерности 1024, что указано в [карточке модели](https://huggingface.co/BAAI/bge-m3).

**Что ты сможешь объяснить:** вектор — числовое представление текста; близость векторов помогает искать связанные по смыслу документы.

Если T4 пока недоступна, маленькую функциональную проверку можно сделать на CPU или локальном GPU. Это отдельная отладочная конфигурация, а основные замеры выполняются на согласованном оборудовании.

### Шаг 7. Собрать dense RAG и провести первый прогон

**Проверка:** любой результат из таблицы можно открыть и проверить до исходных документов и API-вызовов. Отсутствующие/ошибочные ответы не исчезают из знаменателя метрик.

**Что ты сможешь объяснить:** весь путь «вопрос → поиск пяти текстов → ответ → сравнение с эталоном → стоимость».

## 7. Что делаем сейчас, пока доступов нет

Отсутствие API мешает реальным экспериментам, но не мешает подготовить инфраструктуру и научиться ей пользоваться.

| Можно выполнить сейчас | Требует доступа или отдельного решения |
|---|---|
| Проверить RAM, диск, Windows и виртуализацию | Проверить параметры внутреннего API |
| Установить WSL 2 и Docker Desktop | Получить реальный ответ qwen2.5-72b |
| Запустить Langfuse и MLflow | Проверить настоящее поле `usage` и лимиты сервера |
| Отправлять демонстрационные трассы и runs | Поднять эмбеддер именно на выделенной T4 |

| Скачать открытые данные и проверить выборки | Измерить стоимость индексации графовых систем |
| Сделать тесты прокси на искусственных ответах API | Подтвердить, что учёт корректен на реальном API |
| Разобрать 2–3 вопроса и оценку ответов вручную | Получить научные результаты по качеству и стоимости |

Тестовый API возвращает заранее заданный ответ и выдуманное `usage` только для проверки программы. Такие записи маркируются `mode=mock`, хранятся отдельно и исключаются из таблиц исследования и реального токен-бюджета. В отчёте пишем «проверена работа инфраструктуры на тестовых данных», пока реальный API не подключён.

Первые совместные занятия:

1. **Занятие 1:** проверяем ресурсы Windows, разбираем Docker/Compose, начинаем установку WSL 2 и Docker Desktop. Результат — работающий учебный контейнер.
2. **Занятие 2:** запускаем Langfuse, создаём проект и отправляем тестовую трассу. Результат — видим событие из своего скрипта.
3. **Занятие 3:** запускаем MLflow, сохраняем параметры, метрику и файл, проверяем сохранность после перезапуска. Результат — демонстрационный эксперимент.
4. **Занятие 4:** готовим структуру данных и тесты подвыборок; при появлении API переключаем приоритет на шаг 4 основного маршрута.

Доступы запрашиваем сразу. Не закладываем ожидание ответа в оценку длительности установки и не заменяем отсутствующий внутренний API платным внешним сервисом без отдельного решения.

## 9. Как будем выполнять исследовательскую часть

### E1. Сколько стоит подготовка индексов

Для каждой системы сначала измеряем 50–100 пассажей, затем оцениваем полную стоимость по фактическому расходу. Для RAPTOR и LightRAG линейная экстраполяция может быть неточной; это предварительный прогноз, а не готовый результат.

Перед большим запуском фиксируем модель, конфигурацию, корпус и версии. Индексируем два корпуса, отдельно учитываем LLM-токены, время, число вызовов и работу эмбеддера. Сохраняем индекс и его идентификатор, чтобы не строить его повторно при каждом вопросе.

**Готово:** у каждой системы и датасета есть фактическая стоимость индексации `I`, полный журнал вызовов и сохранённый индекс.

### E2. Пилот на 200 вопросах каждого набора

Запускаем системы на одинаковых вопросах и основном фиксированном корпусе. Считаем F1, EM, Recall@5, токены запроса `q` и задержки. Разбираем вручную несколько успехов и ошибок, проверяем, что низкий результат не вызван неправильной интеграцией.

На КТ-5 выбираем графовую систему для каскада по заранее описанному правилу качества и стоимости. Если преимущество графа на MuSiQue меньше 3 процентных пунктов, обсуждаем резервный 2Wiki по условию задания. Сам по себе маленький выигрыш не является ошибкой эксперимента.

**Готово:** таблица пилота, объяснение конфигураций и записанное решение о следующих прогонах.

### E3. Основное сравнение

Расширяем пилот до 500 вопросов на каждом датасете. При неизменной конфигурации переиспользуем уже полученные ответы, добирая остальные вопросы. Ошибки и незавершённые вызовы сохраняем; повторные попытки учитываем в общем расходе проекта.

Проверяем Г1 из задания: на MuSiQue ожидается не менее +5 п.п. F1 у HippoRAG 2 при стоимости запроса не выше трёх стоимостей dense RAG; на HotpotQA ожидается небольшой разрыв, менее 2 п.п. Результаты могут не подтвердить ожидания.

Строим интервалы F1/EM и парных разностей, считаем среднюю стоимость с учётом индексации для 100, 1 000, 10 000 и 100 000 запросов. Рассчитываем токены на верный ответ и существование точки окупаемости.

По исходному плану используем 1 000 bootstrap-перевыборок вопросов и 95%-интервалы. Для разности систем в каждой перевыборке берём одни и те же вопросы у обеих систем — это парный bootstrap. Основные результаты показываем отдельно по датасетам; способ объединения заранее фиксируем. Если есть связанные вопросы, отдельно проверяем необходимость группового ресэмплинга.

**Готово:** таблица «качество × стоимость» со своими измерениями и доверительными интервалами.

### E4. Есть ли смысл выбирать систему для каждого вопроса

Для каждой пары ответов dense RAG / выбранный граф определяем: обе правы, прав только RAG, прав только граф, обе ошиблись. Это дополняемость.

Oracle — мысленный выбор с заранее известными правильными ответами. Он показывает верхнюю границу возможного качества выбора, но не является доступным в реальной работе маршрутизатором. Отдельно считаем oracle по EM и по F1 согласно зафиксированным определениям.

**Готово:** таблица дополняемости и верхняя граница, объясняющая, сколько пользы в принципе может дать маршрутизация.

### E5. Какие признаки помогают обнаруживать ошибки RAG

В порядке практического старта проверяем:

1. **Поддержку ответа контекстом:** встречается ли ответ в найденных текстах. Это лишь признак, а не доказательство правильности.
2. **Разброс близости документов:** насколько первый найденный документ ближе остальных.
3. **Logprobs:** насколько вероятными модель считала токены ответа, если API это поддерживает.
4. **Заявленную уверенность:** число, которое выдаёт сама модель; его полезность надо проверить.
5. **Самосогласие:** совпадают ли ответы при нескольких генерациях. Это требует дополнительных платных по токенам вызовов.

Для каждого сигнала определяем направление шкалы, правила обработки пропусков, AUROC и стоимость. AUROC измеряет, насколько хорошо сигнал отделяет правильные ответы от ошибочных. Начинаем с признаков, которые можно получить из уже сохранённых данных, затем проверяем дополнительные вызовы в пределах бюджета.

**Готово:** таблица сигналов и расходов. Минимальный вариант проекта — один корректно проверенный сигнал.

### E6. Каскад «сначала RAG, затем при необходимости граф»

RAG отвечает первым. При недостаточной уверенности вызываем граф и используем его ответ. Перебираем пороги и получаем точки с разными качеством, стоимостью и долей обращений к графу.

Сравниваем с тремя политиками: всегда RAG, всегда граф, случайно выбирать граф с заданной вероятностью. Все политики получают одинаковые вопросы. Для каскада считаем и уже выполненный RAG, и получение сигнала, и граф на эскалированных запросах.

Порог для итоговой проверки выбираем на обучающей/валидационной части; качество выбранного правила оцениваем на вопросах, которые не использовались для выбора порога. Показанная на всех данных сетка порогов отдельно обозначается как исследовательская кривая.

Каскад и случайное смешивание сравниваем при одинаковой ожидаемой стоимости, используя парный bootstrap по вопросам. Дополнительно считаем AIQ — площадь под кривой качества по стоимости; диапазон и нормировку стоимости задаём заранее и одинаково для сравниваемых политик.

**Готово:** кривые, доверительные интервалы, стоимость сигналов, доля эскалаций и честный ответ, выполнены ли 95%/60%.

### E7. Pre-hoc и гибрид — расширение

Pre-hoc выбирает систему до генерации ответа. Обучаем простые варианты: логистическую регрессию, TF-IDF + SVM, маршрутизатор с ручными признаками; затем при необходимости LightGBM. Гибрид выбирает между RAG, каскадом и немедленным обращением к графу.

Проводим 5-fold кросс-валидацию с тремя сидами. Подбор признаков, преобразований и гиперпараметров не использует проверочную часть соответствующего фолда. Стоимость получения признаков учитывается; признаки по результатам поиска означают, что сам поиск уже выполнен.

**Готово:** оценка реально достижимого качества выбора и разрыва до oracle. Настройка маршрутизатора по заранее сохранённым исходам обычно не требует повторной генерации всех ответов.

### A1–A6 и E8

| Проверка | Что меняем | Зачем |
|---|---|---|
| A1 | Сигнал уверенности по одному и в комбинации | Узнать, какой сигнал помогает |
| A2 | Группы признаков маршрутизатора | Понять вклад длины, сущностей, лексики и поиска |
| A3 | Учитываем или исключаем индексацию | Показать влияние начальных затрат |
| A4 | Модель reader при неизменных индексах | Проверить зависимость результата от модели ответа |
| A5 | Число пассажей: 3, 5, 10 | Проверить влияние объёма контекста |
| A6 | Выбор между двумя или тремя системами | Проверить пользу добавления RAPTOR |
| E8, опционально | Два учебника другого набора | Проверить перенос без переобучения |

При нехватке времени сначала защищаем достоверность E1–E6. Расширения выполняем после проверки остатка токенов и времени; отклонения от требований преподавателя фиксируем заранее.

## 10. Учёт расходов: центральная часть работы

Из исходного задания: общий лимит **90 млн токенов**, плановая часть примерно 75 млн и резерв примерно 15 млн на отладку и повторы.

| Статья | Первоначальная оценка из задания, млн токенов |
|---|---:|
| Индексация HippoRAG 2 на двух корпусах | 30 |
| Индексация LightRAG | 10 |
| Индексация RAPTOR | 3–4 |
| Индексация dense RAG: генеративные LLM-токены | 0 |
| Основные ответы четырёх систем | 15 |
| Самосогласие | около 7 |
| Дополнительные модели reader | 8 |
| Резерв и округление до общего лимита | около 15–17 |

Это оценки исходного документа, не цены сервисов и не наши измерения. Их надо пересчитать после малых запусков. «0» у индексации dense RAG относится к генеративным LLM-токенам: время и ресурсы эмбеддера при этом расходуются.

Для одного запроса после `N` обращений к уже подготовленному корпусу:

```text
C(N) = I / N + q

I — стоимость однократной индексации в токенах;
q — средний расход на один запрос;
N — число запросов между перестроениями индекса.
```

Иллюстрация с выдуманными числами: индекс стоил 1 000 000 токенов, запрос — 2 000. При 100 вопросах средняя стоимость равна 12 000 токенов, при 10 000 — 2 100. Чем больше вопросов обслужил тот же индекс, тем меньше его доля на вопрос. Если корпус обновился и индекс перестроен, учитываем новые затраты.

Для каскада:

```text
q_cascade = среднее по вопросам(
    токены RAG
    + токены получения сигнала
    + индикатор_эскалации × токены графа
)

C_cascade(N) = (I_RAG + I_graph) / N + q_cascade
```

Общие реально переиспользуемые операции не дублируем в учёте, но уже выполненный ответ RAG нельзя считать бесплатным. При разных расходах графа на разных вопросах используем сумму по фактически эскалированным вопросам, а не произведение доли эскалаций на произвольное среднее.

Два отдельных учёта:

1. **Бюджет проекта:** все реальные токены, включая отладку, неудачные запуски, повторы и эксперименты с другими настройками.
2. **Стоимость исследуемой системы:** стоимость выполнения зафиксированного протокола. Она восстанавливается по первичным записям и не обнуляется из-за того, что мы повторно построили график по сохранённым ответам.

Схема записи вызова:

```text
run_id, request_id, system, dataset, phase,
qid или document_id, model, input_tokens, output_tokens,
duration_ms, status, attempt, cache_hit, usage_source
```

Для индексации нет обычного `qid`: указываем документ/пакет. В MLflow дополнительно храним его собственный ID run и привязку к общему `run_id`, Git commit, хэшу корпуса и конфигурации. Идентификаторы разных сервисов не обязаны совпадать автоматически.

Обязательные проверки реализации:

- Все обращения к LLM проходят через учёт, включая служебные вызовы библиотек.
- Прокси получает принадлежность запроса явно; параллельные вызовы не используют одну изменяемую глобальную переменную для `qid` или `system`.
- Один вызов не суммируется дважды из-за вложенных spans или одновременной автоматической и ручной трассировки.
- Реально выполненные повторные попытки попадают в бюджет; если после сетевой ошибки расход неизвестен, это отмечается и сверяется с сервером, когда возможно.
- Перед остановкой короткого скрипта дожидаемся отправки телеметрии; JSONL остаётся независимым первичным журналом.
- Индекс сохраняется и переиспользуется. Кэши готовых LLM-ответов не маскируют расход измерительного прогона.
- Перед большим запуском есть прогноз и ограничение расходов. Отклонение более 10% от плановой статьи обсуждаем с преподавателем в тот же день, как требует задание.
- Еженедельно сверяем локальные суммы и Langfuse, записываем остаток от 90 млн.

## 11. Уточнения протокола до больших экспериментов

Эти пункты пока не надо запоминать. Они нужны нам при реализации, чтобы не получить красивую, но неверную таблицу. Ниже — предлагаемые уточнения исходного задания, а не уже согласованные изменения требований.

**1. Что означает «верный ответ».** F1 измеряет частичное совпадение слов, а EM — полное совпадение после нормализации. Для «токенов на верный ответ» предлагается использовать `accuracy = EM / 100`, то есть долю правильных ответов от 0 до 1. Деление на F1 — другая метрика, её нельзя незаметно назвать долей верных ответов. Определение accuracy и меток oracle фиксируем до анализа.

**2. Что означает Recall@5.** Это доля нужных supporting-пассажей, найденных среди первых пяти результатов: `число найденных supporting / общее число supporting`. Деление на пять означало бы precision, другую метрику. В исходном глоссарии формулировка неоднозначна; ориентируемся на проверенную реализацию оценки.

**3. Что сравниваем у RAPTOR и LightRAG.** Эти системы могут возвращать суммаризации или факты графа вместо пяти исходных пассажей. До E2 фиксируем способ формирования контекста, его лимит и связь с исходными документами. Нельзя засчитать все документы под узлом дерева как реально прочитанные supporting-пассажи. Если корректный passage recall для режима недоступен, явно указываем ограничение и согласуем отдельную метрику. Общий reader сам по себе ещё не гарантирует одинаковый объём доказательств.

**4. Два представления стоимости.** Показываем отдельно `q` без индексации и `C(N)` с индексацией. Критерий 95%/60% в исходной формулировке относится к стоимости запроса; дополнительно строим результаты с амортизацией при заданных N. Для каскада и смешивания, использующих оба индекса, учитываем стоимость подготовки обоих. Поэтому прямая случайного смешивания корректна для ожидаемой F1 и стоимости запросов; при включении индексации она не обязана соединять точки систем с единственным индексом.

**5. Крайние режимы каскада.** Если все вопросы отправились в граф, конечные ответы совпадают с always-graph, но стоимость обычного каскада выше: RAG уже был выполнен. Проверка из исходного задания должна различать равенство ответов и расходов. Для крайних случаев используем явные режимы «никогда не эскалировать» и «всегда эскалировать»: условие `u < 1` не отправляет в граф запросы с `u = 1`.

**6. Как выбирается порог.** Нельзя найти лучший порог по эталонам всех 1 000 вопросов и заявить качество на тех же вопросах как независимую проверку. Пороги и обучаемые комбинации сигналов настраиваются внутри train/validation, итоговая оценка — по отложенным предсказаниям. Для объединённых данных сохраняем представительство обоих датасетов; связанные/повторяющиеся вопросы при необходимости группируем.

**7. Что считать отсутствием разницы.** Интервал разности, содержащий ноль, сам по себе не доказывает «разрыв меньше 2 п.п.». Для такого вывода нужна заранее выбранная проверка эквивалентности или согласованный критерий, например интервал, целиком находящийся в пределах от −2 до +2 п.п. Широкий интервал означает, что данных недостаточно для точного вывода.

**8. Когда существует окупаемость.** При положительных accuracy равенство стоимости на верный ответ даёт:

```text
N* = (I_graph / a_graph - I_rag / a_rag)
     / (q_rag / a_rag - q_graph / a_graph)
```

После вычисления проверяем знак и фактическое неравенство по обе стороны точки. Если индекс графа дороже, а расход на правильный ответ без индексации не лучше RAG, конечной точки окупаемости нет. При accuracy = 0 показатель не определён/бесконечен; деление на ноль не заменяем удобным числом. Исследование может закончиться выводом «не окупается на рассмотренном диапазоне», не требуя положительного N*.

**9. Как интерпретируем oracle.** Маленькая разница oracle − always-graph ограничивает возможный прирост качества от выбора. Она не исключает экономию: часть вопросов всё равно может решаться дешёвым RAG. Провал Г2 также не доказывает автоматически малую дополняемость — причиной могут быть плохой сигнал, высокая стоимость самосогласия или неудачное правило выбора.

**10. Как сокращаем бюджет.** Переход с 72B на 32B может изменить скорость и доступность сервера, но не гарантирует уменьшения числа токенов. До смены модели считаем последствия: переиндексация тоже расходует бюджет. Уменьшение корпуса допустимо только с сохранением всех supporting-пассажей; сокращение числа сэмплов уверенности и числа возвращаемых пассажей — разные изменения. Каждую изменённую конфигурацию обозначаем отдельно.

**11. Как используем пилот и литературу.** Выбор лучшей системы или замена MuSiQue на 2Wiki после просмотра результатов влияют на интерпретацию. Сохраняем результат исходного пилота, описываем правило решения и финальную независимую оценку. Цифры, названия публикаций, доступность кода и заявления о научной новизне из задания перепроверяем по первоисточникам перед статьёй; этот план не подтверждает автоматически все утверждения обзора.

**12. Воспроизводимость и кэши.** Фиксированный seed не обещает полного совпадения всех ответов удалённой модели. Сохраняем реальные ответы, версии, параметры, идентификаторы данных и кэш-статус. Повторный расчёт метрик по готовым ответам выполняется без новых токенов, но его не выдаём за новое измерение онлайн-стоимости.

## 13. Что изучать по ходу работы

Не нужно сначала проходить большой курс по всем технологиям. Каждый теоретический блок связываем с конкретным действием.

| Когда | Что изучить | Как проверить понимание |
|---|---|---|
| До первого сервиса | Терминал, папки, путь, процесс, порт | Объяснить, из какой папки запущена команда и где открыть сервис |
| При Docker | Образ, контейнер, Compose, том, лог | Самостоятельно запустить/остановить сервис и найти ошибку в логах |
| При Langfuse/MLflow | Trace, вызов, run, параметр, метрика, артефакт | Открыть один запрос и связанный эксперимент |
| При API | HTTP-запрос, JSON, адрес, ключ, `usage` | Найти ответ модели и объяснить расход токенов |
| При dense RAG | Вектор, косинусная близость, top-k, reader | Пройти один вопрос от поиска до ответа |
| При графах | Сущность, отношение, OpenIE, PPR | На маленьком примере показать путь между документами |
| При RAPTOR | Кластеризация и суммаризация | Нарисовать дерево из нескольких текстов |
| При оценке | F1, EM, recall, среднее, доверительный интервал | Объяснить ошибку поиска отдельно от ошибки reader |
| При маршрутизации | Уверенность, порог, эскалация, oracle | Объяснить, почему один вопрос пошёл в граф, а другой нет |

Формат нашей работы: ты называешь текущий шаг и показываешь результат команды или ошибку; я объясняю действие, помогаю с кодом и проверкой; после успешного шага сохраняем короткую запись. Если доступны инструменты работы с окружением, технические проверки и изменения выполняем прямо в проекте. Действия в установщике и получение учебных доступов могут потребовать твоего участия.

После каждого шага ты своими словами отвечаешь на три вопроса: «что запустили?», «зачем это нужно?» и «как проверили, что работает?». Это одновременно подготовка к защите.
