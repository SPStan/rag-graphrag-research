## 1. Суть темы

Исследуется, при каких типах вопросов и при каком числе запросов графовый поиск (GraphRAG) окупается против векторного RAG, если считать полную стоимость — токены индексации и запроса — на одной открытой модели. Новизна: cost-controlled сравнение четырёх готовых систем (dense RAG, RAPTOR, LightRAG, HippoRAG 2) с амортизацией индексации и точкой безубыточности по числу запросов, чего нет ни в GraphRAG-Bench, ни в HippoRAG 2, и интерпретируемый каскад «RAG → граф по уверенности ответа» как альтернатива RL-маршрутизаторам 2026 года. Ожидаемый результат: таблица «качество × стоимость» и точка безубыточности на подвыборках MuSiQue и HotpotQA, кривая каскада против «всегда RAG», «всегда граф» и случайного смешивания с bootstrap-интервалами, ответ на вопрос, достигает ли каскад ≥ 95 % качества графа при ≤ 60 % его стоимости. Артефакты — воспроизводимый репозиторий с адаптерами систем и учётом токенов и препринт.

## 2. Глоссарий

Область и системы.

- **LLM** — большая языковая модель; принимает текст (промпт), возвращает текст. Работа модели оплачивается токенами — единицами текста длиной около 3/4 слова.
- **OpenAI-совместимый API** — HTTP-интерфейс `/v1/chat/completions` и `/v1/embeddings`; параметр `base_url` переключает клиентскую библиотеку `openai` на внутренний сервер.
- **vLLM** — сервер, раздающий открытые модели через OpenAI-совместимый API; на T4 используется для эмбеддера.
- **Эмбеддер, эмбеддинг** — модель, переводящая текст в вектор чисел; близкие по смыслу тексты дают близкие векторы (косинусная близость).
- **bge-m3** — открытый многоязычный эмбеддер (568M параметров, вектор 1024), помещается на T4.
- **Пассаж, корпус** — пассаж: фрагмент текста ≈ 100–200 слов с заголовком; корпус: множество пассажей, по которому ищется ответ.
- **RAG (retrieval-augmented generation)** — по вопросу извлекаются k ближайших пассажей, LLM отвечает по ним.
- **Dense RAG, dense retrieval, векторный поиск** — извлечение по косинусной близости эмбеддингов вопроса и пассажей; **top-k** — k лучших пассажей (у нас k = 5).
- **Reader** — вызов LLM, который по вопросу и пассажам выдаёт короткий ответ.
- **GraphRAG** — семейство методов, где при индексации LLM строит из корпуса структуру (граф, дерево), а поиск идёт по ней.
- **Граф знаний (KG), триплет** — граф с узлами-сущностями и рёбрами-отношениями; триплет: (субъект, отношение, объект).
- **OpenIE, NER** — извлечение триплетов из текста без заданной схемы; распознавание именованных сущностей. **GLiNER** — малая открытая NER-модель, работает на T4.
- **HippoRAG 2** — GraphRAG: OpenIE-триплеты + узлы-пассажи в одном графе; поиск — **PPR (Personalized PageRank)**: случайное блуждание по графу от узлов, близких к вопросу; пассажи ранжируются по накопленной вероятности.
- **LightRAG** — GraphRAG: граф сущностей и отношений; **двухуровневый поиск** — по конкретным сущностям (local) и по темам (global); **gleaning** — повторные вызовы LLM для дополнительного извлечения. Режимы: naive, local, global, hybrid, mix.
- **RAPTOR** — дерево: пассажи кластеризуются, LLM суммаризует кластеры, суммаризации кластеризуются снова; поиск — по всем уровням дерева.
- **MS GraphRAG** — GraphRAG от Microsoft с сообществами графа и их суммаризациями; в работе описывается, не запускается (331K токенов на запрос).
- **nano-graphrag, HyperGraphRAG, LinearRAG** — другие открытые GraphRAG-системы: первая (~1K строк, MIT) — план Б вместо LightRAG, две другие встречаются в чужих сравнениях.
- **NV-Embed-v2, Llama-3.3-70B** — эмбеддер (7B параметров, на T4 не помещается) и модель, на которых получены опубликованные числа HippoRAG 2; наши аналоги — bge-m3 и qwen2.5-72b.
- **Индексация** — фаза построения индекса (векторов, графа, дерева) до первого вопроса; для графовых систем стоит миллионы токенов.
- **Multi-hop QA, хоп** — вопрос, ответ на который требует цепочки из 2–4 фактов (хопов) из разных пассажей.
- **Supporting-пассаж, дистрактор** — пассаж, необходимый для ответа; пассаж корпуса, не нужный для ответа.

Стоимость и маршрутизация.

- **Cost-controlled сравнение** — сравнение систем при одинаковой модели, эмбеддере и данных с явным подсчётом токенов каждой.
- **Cost-модель C(N) = I/N + q** — средняя стоимость одного запроса при N запросах: I — токены индексации, q — токены на запрос; **амортизация** — распределение I по N запросам.
- **Точка безубыточности N\*** — число запросов, начиная с которого граф дешевле RAG по токенам на верный ответ.
- **Токены на верный ответ** — C(N) / accuracy; сколько токенов в среднем уходит на один правильный ответ.
- **Маршрутизация** — выбор системы (RAG или граф) для каждого запроса. **Pre-hoc маршрутизатор** решает по признакам вопроса до запуска систем; **post-hoc / каскад** сначала запускает RAG и решает по результату.
- **Каскад «RAG → граф»** — RAG отвечает; при уверенности u ниже порога **τ** запрос уходит в графовую систему (**эскалация**).
- **Сигнал уверенности** — число, предсказывающее правильность ответа RAG: **самосогласие** (доля совпадающих ответов среди k сэмплов при temperature > 0), **logprob** (логарифм вероятности токенов ответа, если API его отдаёт), **verbalized confidence** (модель называет уверенность числом), поддержка ответа строкой в пассажах, разброс косинусов top-5.
- **Always-RAG / always-graph** — крайние политики: всё в RAG / всё в граф. **Случайное смешивание** — доля p запросов случайно уходит в граф; даёт прямую между крайними точками на плоскости «качество × стоимость».
- **Oracle** — политика, знающая заранее дешевейшую верно отвечающую систему; верхняя граница любой маршрутизации. **Дополняемость** — доля вопросов, где граф прав, а RAG нет (и наоборот).
- **Кривая «качество × стоимость», AIQ** — F1 как функция средней стоимости запроса при переборе τ; AIQ — площадь под этой кривой (как в RouterBench). **Парето-фронт** — точки, которые нельзя улучшить по одной оси без ухудшения другой.
- **FrugalGPT, Adaptive-RAG** — каскад моделей по порогу уверенности (2023–2024); классификатор сложности вопроса, выбирающий число шагов ретривала (NAACL 2024).
- **SFT, RL** — дообучение модели на примерах; обучение с подкреплением; в GraphRAG-Router так обучают маршрутизатор (чёрный ящик, у нас не используется).
- **OOD** — данные из другого распределения (другой домен), чем обучающие.

Метрики и статистика.

- **F1, EM** — F1: перекрытие слов ответа и эталона (0–100); EM: точное совпадение после нормализации. Обе — из скрипта HippoRAG 2, максимум по эталонным ответам.
- **Recall@5** — доля supporting-пассажей среди top-5 извлечённых.
- **AUROC** — площадь под ROC-кривой; 0,5 — сигнал не отличает ошибки RAG от верных ответов, 1,0 — отличает идеально.
- **Логистическая регрессия, бустинг, SVM** — простые классификаторы (библиотеки sklearn, LightGBM); обучаются на T4 за секунды.
- **TF-IDF** — вектор частот слов запроса с весом редкости слова в коллекции; лексические признаки без нейросети. **MiniLM** — малый эмбеддер предложений.
- **Macro-F1** — F1 классификатора, усреднённый по классам с равным весом.
- **LLM-judge, win-rate** — оценка, где другая LLM сравнивает два ответа; доля побед. Так оценивались LightRAG и UltraDomain; у нас не используется.
- **п.п.** — процентный пункт: разность двух процентов (48,6 − 45,7 = 2,9 п.п.).
- **Кросс-валидация (5-fold)** — данные делятся на 5 частей; классификатор обучается на 4, проверяется на 1, по кругу.
- **Сид (seed)** — число, фиксирующее случайность (подвыборка, разбиение, сэмплы LLM).
- **Bootstrap-ДИ** — доверительный интервал: 1 000 раз пересобираем выборку вопросов с возвращением, считаем метрику, берём 2,5 % и 97,5 % квантили. **Парный bootstrap** — то же для разности двух систем на одних вопросах.
- **Минимально различимый эффект** — наименьшая разность, которую выборка данного размера отличает от нуля.
- **Ablation** — выключение одного компонента при прочих равных, чтобы измерить его вклад.

Инфраструктура и артефакты.

- **Langfuse** — self-host сервис трассировки LLM-вызовов: **трейс** (один запрос), **span** (один вызов), **usage** (prompt/completion токены), **теги** (system, phase, qid).
- **HF (Hugging Face)** — хостинг моделей и датасетов; файлы датасетов скачиваются оттуда.
- **fp16** — 16-битные числа для весов модели; bge-m3 в fp16 занимает ≈ 1,2 ГБ памяти T4.
- **TEI (text-embeddings-inference), sentence-transformers, FastAPI** — сервер эмбеддингов от Hugging Face; Python-библиотека для эмбеддеров; библиотека для HTTP-серверов на Python.
- **Docker, venv** — контейнеры (Langfuse запускается в Docker); изолированное Python-окружение с зафиксированными версиями.
- **Smoke-тест** — минимальная проверка, что компонент отвечает (один запрос к API, один вектор от эмбеддера).
- **jsonl, run_id** — файл с одним JSON-объектом на строку; идентификатор прогона, общий для всех его записей.
- **Temperature** — параметр случайности генерации; 0 — детерминированно, 0,7 — для сэмплов самосогласия.
- **JSON-режим, function calling** — режимы API со структурированным выводом; ни одна из четырёх систем их не требует.
- **Препринт** — статья 8–10 страниц на английском, готовая к загрузке на arXiv. **README, `reproduce.sh`** — описание и скрипт полного воспроизведения результатов.
- **КТ** — контрольная точка семестра (недели 2, 5, 9, 12). **5А** — высший балл регламента: артефакты, количественное сравнение, ablation, воспроизводимость, понимание работы.

## 3. Погружение в тему

RAG хранит корпус как векторы пассажей; на запрос эмбеддер кодирует вопрос, ищутся top-5 ближайших пассажей, reader отвечает. Индексация стоит ноль LLM-токенов, запрос — 1–2K токенов. На вопросах с одним фактом это работает: на HotpotQA dense retrieval (NV-Embed-v2 + Llama-3.3-70B) даёт F1 75,3 (arXiv 2502.14802). На MuSiQue, где ответ требует 2–4 хопа через разные пассажи, тот же RAG падает до F1 45,7: вектор вопроса близок к первому пассажу цепочки и далёк от остальных.

GraphRAG переносит работу в индексацию. HippoRAG 2 прогоняет каждый пассаж через LLM-OpenIE (≈ 2,7K токенов на пассаж), строит граф «сущности + пассажи» и на запросе запускает PPR — блуждание, которое доходит до пассажей, связанных с вопросом через промежуточные сущности. Результат: F1 48,6 на MuSiQue (+2,9), 71,0 на 2WikiMultiHopQA (+9,5 к dense 61,5) и 75,5 на HotpotQA (+0,2) (arXiv 2502.14802). LightRAG строит граф сущностей с двухуровневым поиском, RAPTOR — дерево суммаризаций. Независимые замеры показывают цену: в GraphRAG-Bench (arXiv 2506.05690) на фактических вопросах базовый RAG 60,9 % против HippoRAG 2 60,1 %, а токены на запрос — MS GraphRAG 331K, LightRAG 101K, HippoRAG 2 1K, RAG 0,95K; по VLDB 2025 (arXiv 2503.04338) графы с отношениями требуют до 40× больше токенов индексации, чем дерево RAPTOR, и RAPTOR выигрывает на простых вопросах. Вывод литературы: граф окупается на multi-hop и проигрывает на простых фактах.

Пробел — в единице измерения. Все сравнения отвечают «какая система лучше на датасете», без амортизации индексации по числу запросов и без выбора на уровне запроса. Маршрутизация даёт резерв: классификатор «RAG или GraphRAG» по запросу прибавляет +1,1 %, интеграция обоих контекстов +6,4 % (arXiv 2502.11371); в RAGRouter-Bench (arXiv 2602.00296) лучший из 13 pre-hoc маршрутизаторов даёт 43,7 % против oracle 60,8 % — разрыв в 17 п.п.; GraphRAG-Router (arXiv 2604.16401) обучает RL-маршрутизатор между пятью GraphRAG-системами и тремя ярусами LLM, снижая вызовы большой модели на 30 %, но код не подтверждён и индексация в стоимость не входит. Каскады по уверенности известны для пар «дешёвая → дорогая модель» (FrugalGPT, arXiv 2305.05176: до 98 % экономии при равной точности) и для числа шагов ретривала (Adaptive-RAG, arXiv 2403.14403); для пары «RAG → граф» при одной модели их не измеряли.

Работа студента — стенд, где четыре готовые системы работают на одной модели (qwen2.5-72b), одном эмбеддере (bge-m3) и одних подвыборках, каждый LLM-вызов учтён в Langfuse, а поверх стенда измеряются точка безубыточности N\*, кривая каскада по уверенности и oracle-граница дополняемости.

Отличие нашей работы: стоимость считается с индексацией и амортизируется по N, результат В1 — точка безубыточности, а маршрутизация проверяется post-hoc каскадом по уверенности с oracle-границей; все четыре системы прогоняются на одной открытой модели и одном эмбеддере, чего нет ни в одной из десяти работ.

## 5. Постановка

В1 (измерительный вопрос). При одной модели, одном эмбеддере и учёте токенов индексации и запроса — на каких вопросах и при каком N графовые системы окупаются против dense RAG?

Г1 (пороги): на MuSiQue HippoRAG 2 даёт ≥ +5 п.п. F1 к dense RAG при стоимости запроса ≤ 3× стоимости RAG; на HotpotQA разрыв < 2 п.п.; по токенам на верный ответ C(N)/accuracy граф дешевле RAG только при N ≥ N\*, и N\* измеряется для каждой графовой системы и датасета при N ∈ {10², 10³, 10⁴, 10⁵}.

В2 (главный вопрос). Можно ли выбирать между RAG и графом для каждого запроса так, чтобы сохранить качество графа при меньшей стоимости?

Г2 (пороги X = 95, Y = 60 зафиксированы до экспериментов): каскад «RAG → граф по уверенности» и/или pre-hoc маршрутизатор достигают ≥ 95 % F1 режима always-graph при ≤ 60 % его стоимости на запрос, и кривая «F1 × стоимость» каскада лежит выше прямой случайного смешивания always-RAG и always-graph (парный bootstrap, ДИ разности не содержит нуля).

Критерий успеха работы: Г1 проверена с ДИ на 2 датасетах × 4 системах; Г2 проверена на объединённых 1 000 вопросах с кривыми и ДИ; N\* и oracle-граница опубликованы.

Отрицательный результат. Если Г1 не подтверждается — публикуется первое cost-controlled сравнение четырёх систем на открытой 72B-модели с индексацией: «граф не окупается при бюджете < Z токенов» с числом Z. Если Г2 не подтверждается — дополняемость RAG и графа по вопросам мала (oracle − always-graph < 3 п.п.), у маршрутизации нет резерва; вывод подкрепляется oracle-границей и AUROC сигналов.

## 8. Что делает студент: метод и архитектура

Свои компоненты.

1. **Embedding-сервер** на T4: bge-m3 в fp16 через vLLM (режим embedding) или text-embeddings-inference с endpoint `/v1/embeddings`; при проблемах — FastAPI-обёртка над sentence-transformers (~40 строк). Студент объясняет: как вычисляется вектор, почему один эмбеддер для всех систем обязателен.
2. **Прокси учёта стоимости** (`eval/cost_proxy.py`, ~150 строк): FastAPI-сервер, запускаемый в процессе цикла оценки, пересылает `/v1/chat/completions` во внутренний API, читает `usage`, записывает span в Langfuse с тегами (system, phase ∈ {index, query, confidence}, qid, run_id) из контекста, который цикл выставляет перед каждым вопросом; дублирует записи в `results/*.jsonl`. Все четыре системы получают `base_url` прокси. Студент объясняет: откуда берётся каждое число токенов в таблицах.
3. **Cost-модель** (`eval/cost.py`): I и q по системам и датасетам; C(N) = I/N + q; токены на верный ответ C(N)/accuracy; N\* — решение C_graph(N)/acc_graph = C_rag(N)/acc_rag.
4. **Сигналы уверенности** (`router/signals.py`): самосогласие k = 5 (temperature 0,7, доля ответов, совпадающих по EM с ответом при temperature 0); средний logprob токенов ответа (если API отдаёт `logprobs`); verbalized confidence (reader называет число 0–100 в том же вызове); поддержка ответа подстрокой в top-5 пассажах; разброс косинусов top-5 (cos₁ − cos₅). Стоимость каждого сигнала учитывается в стоимости каскада.
5. **Каскад** (`router/cascade.py`): u < τ → запрос уходит в лучшую по В1 графовую систему (ожидается HippoRAG 2); перебор τ по сетке даёт кривую «F1 × средняя стоимость»; точка с минимальной стоимостью при F1 ≥ 0,95 · F1_graph — ответ на Г2.
6. **Pre-hoc маршрутизатор** (`router/prehoc.py`): логистическая регрессия и LightGBM на признаках вопроса (длина, число сущностей по GLiNER, слова сравнения и мостов «which», «both», «after», разброс косинусов top-5, TF-IDF); метка — дешевейшая верно ответившая система из В1; 5-fold кросс-валидация, 3 сида разбиений.
7. **Гибрид** (`router/hybrid.py`): pre-hoc решает «RAG / каскад / сразу граф».
8. **Статистика** (`eval/bootstrap.py`): bootstrap-ДИ, парный bootstrap, AUROC.

Переиспользуемые компоненты и что студент должен уметь объяснить: HippoRAG 2 — OpenIE, устройство графа «сущности + пассажи», PPR, роль `linking_top_k` и `qa_top_k`; LightRAG — извлечение сущностей и отношений, gleaning, различие local/global/hybrid, почему стоимость запроса ≤ 8K; RAPTOR — кластеризация, уровни дерева, какие узлы попадают в top-5; bge-m3 — вход, выход, косинусная близость; скрипт оценки HippoRAG 2 — нормализация ответа, F1 по словам, максимум по эталонам, recall@5. К КТ-5 студент описывает пайплайн каждой системы в README своими словами (по 10–15 строк).

Модели: qwen2.5-72b — индексация и чтение во всех системах (класс Llama-3.3-70B протокола HippoRAG 2); qwen3-32b и gpt-oss-120b — только ablation чтения на тех же индексах (у qwen3-32b отключить режим размышления, у gpt-oss-120b — низкий reasoning effort, иначе токены ответа несопоставимы); gemma4-31b — резерв. На T4: bge-m3, GLiNER, sklearn/LightGBM, bootstrap.

Контракт компонента (входит в артефакты): `RetrievalBackend.index(corpus) → cost`, `RetrievalBackend.query(q, k) → passages, cost`, `Router.decide(q, signals) → backend | cascade`; схема тегов Langfuse разделяет стоимость индексации и запроса.

Сиды фиксируются в `configs/`.

## 11. Минимально достаточный результат

Если каскад и маршрутизатор не выходят выше прямой смешивания, защищается В1: cost-controlled сравнение трёх–четырёх систем на двух датасетах при одной модели, с индексацией, ДИ, N\* и oracle-границей, объясняющей отсутствие резерва. Это уровень 4С–4В. Уровень 3D — если не воспроизведена ни одна графовая система; тогда обязательны dense RAG с ДИ, таблица стоимости индексации по логам неудачных запусков и разбор причин.

## 13. Что сдать

Репозиторий:

```
backends/   dense.py, raptor.py, lightrag.py, hipporag2.py — адаптеры под RetrievalBackend

eval/       hipporag_eval.py (обёртка F1/EM/recall@5), cost_proxy.py, cost.py, bootstrap.py

scripts/    reproduce.sh
README.md   постановка, таблица результатов, установка, запуск, описание четырёх систем
```

README: постановка В1/В2 с порогами; установка (зафиксированные версии, переменные окружения `OPENAI_BASE_URL`, `OPENAI_API_KEY`, адрес embedding-сервера); запуск каждой фазы одной командой; таблица результатов с ДИ; ограничения (два датасета, одна модель, урезанные корпуса). Тесты: детерминизм подвыборок; прокси считает `usage` и теги; каскад при τ = 0 совпадает с always-RAG, при τ = 1 — с always-graph. `reproduce.sh` за ≤ 30 минут на 20 вопросах повторяет пайплайн от подвыборки до кривой.

Препринт (8–10 страниц, английский): 1. Introduction — задача и cost-модель; 2. Related work — десять работ раздела 4; 3. Protocol — данные, подвыборки, модели, учёт стоимости; 4. Systems — четыре системы и адаптеры; 5. Cascade and router; 6. Results В1 с N\*; 7. Results В2 с кривыми и критерием X/Y; 8. Ablations; 9. Limitations; 10. Reproducibility.

Презентация (12–15 слайдов): постановка → cost-модель → стенд → таблица В1 → N\* → кривые В2 → ablation → ограничения → отличия от GraphRAG-Router / RAGRouter-Bench / GraphRAG-Bench.

## 14. Правила работы

Коммиты — каждую неделю семестра; результаты каждого прогона — в `results/` с run_id и суммой токенов по фазам; сумма токенов по Langfuse сверяется с лимитом 90M каждую неделю и указывается в апдейте.

Шаблон еженедельного апдейта (понедельник, ≤ 15 строк):

```
Неделя N (даты)
Сделано: ...
Числа: (система, датасет, метрика, ДИ, токены)
Токены за неделю / накопительно: ... / ... из 90M
Блокеры: ...
План на неделю N+1: ...
Вопросы руководителю: ...
```

Что и когда спрашивать у руководителя: в неделю 1 — доступ к API и параметры (`logprobs`, лимиты запросов в минуту); на КТ-2 — утверждение X/Y и плана сокращения; на КТ-5 — решение о 2Wiki и о полюсе «граф»; при любом отклонении бюджета > 10 % от таблицы раздела 6 — в тот же день; при неработающей системе > 3 дней — план Б без ожидания следующей встречи.

Чек-лист самопроверки перед защитой:

- [ ] Все системы прогнаны на одной модели, одном эмбеддере, одних id; чужие числа в таблицах результатов отсутствуют.
- [ ] Для каждой системы есть I, q, F1/EM, recall@5 с bootstrap-ДИ; N\* и токены на верный ответ при четырёх N.
- [ ] Г1 и Г2 проверены против зафиксированных порогов; отрицательные исходы интерпретированы.
- [ ] Кривая каскада сравнена с прямой смешивания парным bootstrap; oracle-граница приведена.
- [ ] Ablation A1–A6 выполнены; 3 сида для маршрутизатора.
- [ ] README воспроизводит результаты; `reproduce.sh` проходит; тесты зелёные; секретов в репозитории нет.
- [ ] Препринт по разделам 1–10; презентация отвечает на отличия от GraphRAG-Router, RAGRouter-Bench, GraphRAG-Bench.
- [ ] Могу объяснить PPR, дерево RAPTOR, двухуровневый поиск LightRAG, каждый сигнал уверенности, cost-модель и bootstrap.
